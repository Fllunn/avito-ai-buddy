# Ревью backend AI-buddy — 14.11.2026

## Итог и основание

Подтверждены **4 продуктовых дефекта: 3 × P1, 1 × P2**. Все четыре воспроизведены адресными тестами в изолированной временной копии с одноразовым PostgreSQL и детерминированными подменами внешнего сервиса/LLM. Падение этих тестов означает нарушение проверяемого инварианта, а не ошибку запуска.

Проверялась текущая рабочая копия, а не только HEAD и не удалённый deployment. Все 135 SHA-256 из `output/backend-review/2026-11-14/source-manifest.json` совпали. Прочитаны корневые и локальные инструкции, архитектура, ADR 0004/0006/0009/0010/0011, тематические спецификации утверждённого `build-onboarding-prototype` и реализация журнала redesign. `openspec/specs/` не содержит текущих spec-файлов; контракты взяты из change, на который ссылается архитектура. Неутверждённые предположения о желаемом поведении не использовались как требования.

Исходники проекта не исправлялись. Отчёт, тестовые свидетельства и копии экспериментальных тестов сохранены только в `output/astra-review/`. Commit/push/PR не выполнялись. Реальная LLM и production не вызывались, секретные конфигурации не открывались. Работа последовательная, без подагентов. Полный повтор автоматических проверок не выполнялся.

## Подтверждённые дефекты

### R1 · P1 · Ответ модели может подтвердить действие вопреки тексту пользователя

**Место:** `backend/internal/api/processing.go:528` и `:548`; поступление намерений модели — `:155`. Аналогичный путь отметки шага — `:530`.

**Триггер:** в диалоге есть одна действующая карточка в `confirm_card`. Пользователь пишет «Пока ничего не отправляй», а провайдер возвращает синтаксически корректный `card_confirm` с confidence=1. Это допустимый выход используемого интерфейса модели, в том числе при ошибке классификации или воздействии недоверенного контекста.

**Путь и последствие:** POST сообщения → Recognizer → `recognized.Data.Intents` → ветка `card_confirm` → `ConfirmCard` → устойчивая попытка → worker → внешняя мутация. Go проверяет состояние, владельца и версию, но не наличие согласия в пользовательском тексте. Сгенерированный моделью класс намерения становится доказательством согласия.

**Контракт:** `assistant-dialogue/spec.md`, «Инструкции и действия» — ответ модели сам по себе не вызывает изменения сервиса; `confirmed-actions/spec.md`, «Версии карточки» и «Проверки подтверждения»; корневое правило явного подтверждения изменения состояния. Авторитет сохранённой попытки защищает последующие вызовы, но здесь сама попытка создаётся без действительного согласия.

**Доказательство:** `TestAstraModelCannotAuthorize`, `reproduction-api.log`: `worker=<nil> external_mutations=1`. Использован контролируемый провайдер, реальная модель не вызывалась. Это доказательство отсутствия границы авторизации, **не** доказательство успешного jailbreak конкретной внешней модели и не оценка его вероятности. Стандартный `agent.Fake` классифицирует простое «да» детерминированно и сам этот дефект не демонстрирует.

**Направление исправления:** выделить подтверждение из свободной классификации: кнопка с конкретным ID/версией либо узкий детерминированный разбор явного согласия в ожидаемом состоянии. Модель может предложить намерение, но не должна создавать свидетельство подтверждения. То же правило применить к ручным шагам.

### R2 · P1 · GET job возвращает закрытый ответ после отзыва доступа к документу

**Место:** `backend/internal/api/business.go:377–387`; `backend/internal/storage/runtime.go:29`, `:224`.

**Триггер:** пользователь получил ответ по доступному документу; затем документ перестал быть доступным его роли/команде. Пользователь повторно читает известный ID job через `GET /api/jobs/{id}`.

**Путь и последствие:** `CompleteMessage` сохраняет полный result с `answer.text` и sources в jobs; `getJob` проверяет сессию и владельца job, затем возвращает сохранённый result без проверки источников. Недоступные фрагменты и названия снова раскрываются. UUID не является защитой: он уже выдан владельцу при принятии сообщения, а журнал также выдаёт связи с job.

**Существующая защита и обход:** `/api/chat` вызывает `AuthorizedHistory` и скрывает этот же ответ по актуальному набору разрешённых документов. Эта защита отсутствует в альтернативном endpoint. Это не доступ к чужому user_id, а обход отзыва прав на вложенные данные собственного job.

**Контракт:** `identity-and-permissions/spec.md`, «Проверки до раскрытия и выполнения»; архитектурное обещание фильтрации истории по текущим правам.

**Доказательство:** `TestAstraJobRechecksDocumentAccess`, `reproduction-api.log`. После смены ролей источников на manager история содержит «Прежний ответ скрыт», но job отвечает HTTP 200 и возвращает побайтно прежний ответ: `unchanged=true`.

**Направление исправления:** выдавать минимальный DTO состояния job либо применять единую текущую авторизацию всех вложенных источников перед выдачей result. Не ограничивать исправление только текстом: sources, карточки и прочие metadata также несут данные.

### R3 · P1 · GET attempt раскрывает параметры скрытого ресурса

**Место:** `backend/internal/api/business.go:365–375`; `backend/internal/storage/attempts.go:126`.

**Триггер:** собственная попытка уже существует, после чего ресурс переводится в hidden. Пользователь читает сохранённый ID попытки.

**Путь и последствие:** `Attempt` проверяет только `a.id` и `a.user_id`; HTTP отдаёт целую попытку, включая parameters и, при наличии, result. В результате раскрывается идентификатор скрытого ресурса, обоснование и сохранённые сведения. Для воспроизведения достаточно queued-попытки; результат сервиса не требуется.

**Существующая защита и обход:** `GET /api/cards/{id}` проходит `decorate` и при тех же правах возвращает 404. Прямой endpoint попытки эту проверку обходит. Для отмены ресурс нужно определять по связанному объекту, поэтому одного поиска `parameters.resource_id` недостаточно.

**Контракт:** `identity-and-permissions/spec.md`, «Скрытый ресурс» и «Права отозваны»: скрытый объект обрабатывается как отсутствующий, закрытые детали не раскрываются.

**Доказательство:** `TestAstraAttemptRechecksResourceVisibility`, `reproduction-domain.log`: `hidden resource card=404 attempt=200`; ответ попытки содержит `monitoring` после `resources.kind='hidden'`. Изменение политики выполнено только в тестовой БД. Наличие публичного интерфейса редактирования политики для триггера не требуется: контракт явно предусматривает отзыв прав.

**Направление исправления:** защищённая проекция попытки с проверкой актуальной видимости её предмета и результата. Унифицировать её с карточками, job и историей. Служебный доступ worker к Authority отделить от пользовательского DTO.

### R4 · P2 · Позднее состояние старой заявки откатывает P6 при уже выданном доступе

**Место:** `backend/internal/storage/results.go:190–195`; ранний выход для той же версии — `:175–182`.

**Триггер:** на один командный ресурс существовали две последовательные заявки. Старую отклонили, после повторной подачи новую одобрили. API уже сохранил approved новой заявки, но ещё не получил новую rejected-версию старой. Поздний refresh доставляет её.

**Путь и последствие:** `saveObject` обеспечивает монотонность **отдельного object_id**, но каждое принятое состояние любой заявки безусловно перезаписывает общий P6. Поздний rejected старого объекта меняет done на attention. Затем повтор approved новой заявки с уже сохранённой версией завершает обработку до пересчёта P6. Ошибка сохраняется и блокирует P7, хотя доступ выдан.

Такое расписание возможно без нарушения сервиса: preflight читает актуальные rejected/grants из remote, но не сохраняет каждое прочитанное состояние в локальную проекцию. Потоки отправки и refresh независимы. Объекты могут приходить с разным запаздыванием.

**Контракт:** `access-requests/spec.md`, «Подтверждение и состояние плана», сценарий «Доступ выдан»: approved командного пространства завершает P6 и разблокирует P7. `confirmed-actions/spec.md`, «Защита от запоздавшего статуса».

**Доказательство:** `TestAstraOldRequestMustNotUndoNewGrant`, `reproduction-domain.log`. Последовательность через реальный `Store.ApplyObject`: A/created/v1 → B/approved/v3 → A/rejected/v2 → повтор B/approved/v3. Итог `P6=attention`. Каждый объект проходит проверку схемы и владельца; версия каждого объекта только растёт. Проверка выполнена на уровне слоя обработки ответов, не полным HTTP-сценарием имитации.

**Направление исправления:** вычислять P6 из совокупного актуального состояния ресурса/выданного доступа, а не из последнего обработанного объекта. Синхронизировать пересчёт по `(user, resource)` и покрыть перестановки ответов нескольких заявок, включая повтор текущей версии.

## Тестовая инфраструктура и прежние падения

1. **Подтверждённая неизолированность storage-фикстуры.** `storage_test.go:17` открывает общую TEST_API_DATABASE_URL, затем делает Migrate/Seed. `Seed` (`storage.go:78`) использует `ON CONFLICT DO NOTHING`, не очищает jobs/cards/executions/objects. `jobFixture` (`worker_test.go:19`) использует того же пользователя, а cleanup завершает только job своей попытки. Повтор/перестановка тестов сохраняет чужие черновики и факты.
2. **Конкретный механизм EXECUTION_CONFLICT.** `testStore` устанавливает операционное время 11.01.2027; `jobFixture` переводит его на 12.11.2026. Замена оставшегося черновика пытается записать факт раньше `execution_runs.updated_at`; `executions.go:117` правильно отвергает обратное время. Адресный `TestAstraFixtureClockRetention` воспроизводит этот механизм на чистой БД. Это тестовый дефект, а не доказательство поломки обычного worker при монотонных часах. Не утверждается, что этим объясняется каждое падение исходного набора.
3. **API timeout — отдельный случай.** `businessFixture` создаёт отдельную schema, поэтому объяснять его падение общей storage-БД нельзя. В `executions_test.go:260` общий LLM timeout равен 5 мс и включает построение контекста до вызова провайдера. При задержке БД deadline может наступить до вызова модели; проверка обязательного failed model-node становится зависимой от тайминга. Это обоснованный кандидат причины, отдельного принудительного воспроизведения задержки не делалось.
4. Прежние browser failures не переведены в продуктовые дефекты: из исходной сводки известны ошибки старых UI-селекторов и зависимость reset от общей истории. Актуальные четыре redesign-сценария и reset на чистом стенде прошли в предыдущем прогоне. Здесь браузер не запускался.
5. Линтер, goimports и `go mod verify` с local replace не пересказывались как ошибки бизнес-логики. Зелёное покрытие не закрывает четыре найденных пути.

## Гипотезы и пробелы тестов

- **Отзыв прав между Validate и Execute.** Worker получает профиль до remote-preflight, затем MarkSending и Execute не перечитывают профиль API; Authority проверяет попытку. Имитация повторно проверяет своего actor в транзакции, что защищает при актуальной политике в её БД. Согласованность отзыва между двумя хранилищами и изменение API-профиля в этом окне требуют отдельного управляемого конкурентного теста. Не включено в подтверждённые дефекты.
- **Изменение ACL документа во время LLM.** `Builder.Current` сравнивает профиль и policy_version, а не повторно читает ACL каждого документа. При изменении ACL без повышения версии пользователя ответ может остаться разрешённым по старому snapshot. Контракт обновления policy_version при административных изменениях не установлен этим ревью; отдельная гонка не воспроизводилась.
- **LLM получает первые 100 сообщений.** `Builder.Build` вызывает `Messages(user,0)`, а SQL читает по возрастанию с LIMIT 100. После длинного диалога свежая история не попадает в контекст. Текущий запрос передаётся отдельно, часть состояния ведётся детерминированно, поэтому конкретное нарушение пользовательского сценария здесь не заявляется. Нужен тест длинной истории с местоименной ссылкой на недавний ответ.
- Недостающие регрессии: недоверенный `card_confirm` при отказе пользователя; отзыв доступа с повторным чтением всех endpoint; отмена со скрытым ресурсом; перестановки статусов нескольких заявок одного ресурса; отзыв прав внутри remote-preflight; принудительное истечение lease между промежуточными шагами диалога.

## Приоритет исправлений

1. Убрать принятие модельного намерения за подтверждение пользователя (R1).
2. Ввести единую авторизованную проекцию пользовательских job/attempt и вложенных данных (R2/R3).
3. Пересчитывать P6 по актуальному состоянию ресурса, включая несколько последовательных заявок (R4).
4. Изолировать storage-тесты по schema/БД, согласовать операционные часы; не лечить загрязнение повторными запусками до зелёного.
5. Добавить перечисленные регрессии; отдельно проверить применимость advisory, не обновляя зависимости вслепую на основании exit code сканера.
