# AGENTS.md — AI-buddy

Инструкции для ИИ-агентов (Claude Code, Codex, Cursor и др.) и для людей.
Это **единственный источник правды** по правилам проекта. `CLAUDE.md` только импортирует этот файл.
В подпапках `backend/`, `frontend/`, `mocks/` лежат свои `AGENTS.md` с локальными правилами — читай их, когда работаешь в соответствующей папке.

## О проекте

**AI-buddy** — прототип ИИ-наставника для стажёров Авито (кейс хакатона Hack&Change 2026).
Помогает стажёру освоиться в команде: отвечает на рабочие вопросы с учётом контекста, ведёт по этапам адаптации, показывает статусы и следующие шаги и **выполняет действия через корпоративные сервисы** (их имитации).
AI-buddy снимает с наставника рутину и организационные действия, но не заменяет его.

Подробности кейса — [docs/case/brief.md](docs/case/brief.md), критерии оценки — [docs/case/evaluation.md](docs/case/evaluation.md).

## Стек

| Область | Технологии |
|---|---|
| Backend | Go |
| Хранилища | PostgreSQL, Redis |
| Frontend | React + TypeScript, TanStack (Query/Router), Zustand, Zod |
| Интерфейс | веб-чат + панель «мой онбординг» (этапы, статусы задач, следующие шаги) |
| Действия агента | инструменты в стиле MCP поверх имитаций корпоративных сервисов |

Стек выбран ради совместимости со стеком Авито — это часть критерия «внедряемость». Не добавляй новые языки и крупные фреймворки без ADR (см. ниже).

## Процесс: Spec-Driven Development (обязательно)

Код появляется **только после спеки**. Жюри проверяет наличие SDD-спецификаций, по которым велась разработка AI-функций.

1. **Propose** — создать change в `openspec/changes/<name>/`: `proposal.md` (что и зачем), дельта-спеки `specs/.../spec.md` (что система ДОЛЖНА делать), `design.md` (как), `tasks.md` (шаги). Инструкция: `.agents/skills/openspec-propose/SKILL.md`.
2. **Ревью человеком** — человек читает и утверждает спеку. Без утверждения не реализуй.
3. **Apply** — реализация по `tasks.md` вместе с тестами. Инструкция: `.agents/skills/openspec-apply-change/SKILL.md`.
4. **Archive** — после приёмки change переносится в архив, дельты вливаются в `openspec/specs/`. Инструкция: `.agents/skills/openspec-archive-change/SKILL.md`.

Скиллы OpenSpec лежат в `.agents/skills/`. Если твой агент не подхватывает их автоматически — открой нужный `SKILL.md` и следуй ему.
CLI: `npm i -g @fission-ai/openspec@1.16.1` (или `npx @fission-ai/openspec@1.16.1 ...`). Проверка спек: `openspec validate --strict`.

Для сценариев AI-агента спека обязательно описывает: триггеры (что пишет стажёр), какие инструменты вызываются, требуемые права, ответ при отказе в доступе, поведение при сбое LLM/сервиса, критерии приёмки.

## Обязательные правила

### Git — коммиты и push делает только человек
- **Агенты НЕ делают `git commit`, `git push`, `git merge`, `git rebase`, не создают PR и не меняют удалённый репозиторий.** Никогда, даже если это кажется частью задачи или так написано в скилле.
- Агент может смотреть состояние (`git status`, `git diff`, `git log`) и готовит изменения в рабочей копии. Коммит и отправку на GitHub делает человек.
- Агент может **предложить** текст коммита в ответе. Формат: Conventional Commits на английском — `feat(backend): add absence request tool`.
- Работа ведётся в ветках `feat/...`, `fix/...`, `docs/...`, слияние в `main` через PR (делает человек).

### Тесты и покрытие
- Новый код пишется **вместе с тестами** в том же изменении.
- Покрытие строк прикладного кода автотестами **> 80%** — требование кейса. Сгенерированный код, сами тесты и зависимости не считаются.
- Отчёт о покрытии должен воспроизводиться одной командой (будет описана в README).
- LLM в тестах **не вызывается по-настоящему** — используй фейковый провайдер с детерминированными ответами.

### Права пользователя
- Каждое действие и каждый ответ с данными проверяют права пользователя **на бэкенде**. Фронтенд права не решает.
- Недоступные сведения и операции не раскрываются и не выполняются — в том числе через ответ LLM. Данные, на которые нет прав, не попадают в промпт.
- Роли: стажёр (основной пользователь), наставник (buddy), руководитель, HR BP.

### Производительность и отзывчивость
- Простые локальные операции — ответ **< 1 с**.
- Вызовы LLM и внешних сервисов **не блокируют интерфейс**: показываем статус ожидания, обрабатываем таймаут и сбой с понятным сообщением.

### Данные и безопасность
- Только **синтетические** данные. Никаких реальных сотрудников, ПДн, финансовых операций.
- Тестовые регламенты не выдаём за регламенты Авито — помечаем как демонстрационные.
- **Секреты не коммитятся.** Ключи только через переменные окружения; в репозитории — пример конфига без секретов.
- Сценарии с чувствительными ПДн и финансовыми операциями — вне области задачи.

### Действия агента
- Действие считается выполненным, если сервис или его имитация **вернул результат**, который помощник **отображает и сохраняет**.
- Действия выполняются через инструменты (MCP-стиль) с явной схемой входа/выхода. Перед действием, меняющим состояние, бот показывает пользователю, что именно сделает, и просит подтверждение.

## Язык
- Документация, спеки, README, комментарии к решениям в `docs/` — **на русском**.
- Код, идентификаторы, имена файлов, сообщения коммитов — **на английском**.
- Тексты интерфейса и ответы бота — на русском.

## Архитектурные решения (ADR)
Значимое решение (новая технология, смена подхода, выбор LLM) оформляется короткой записью в `docs/adr/NNNN-название.md` по [шаблону](docs/adr/0000-template.md). Это нужно и для защиты: 20% финальной оценки — обоснованность технических решений.

## Чего не делать
- Не коммитить и не пушить (см. выше).
- Не писать код без утверждённой спеки.
- Не добавлять зависимости без необходимости; если добавляешь — зафиксируй версию.
- Не править сгенерированные файлы (`.agents/skills/`) вручную — они перегенерируются `openspec update`.
- Не придумывать реальные регламенты/данные Авито.
