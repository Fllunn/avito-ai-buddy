## Fullstack 2026 «Каталог AI-ассистентов» — подробно

Это задание Авито почти совпадает с нашей задачей: Go + PostgreSQL + React, роли, LLM за абстракцией, мок-провайдер, история запусков. Требования к нему = ожидания Авито к AI-функциям.

**Предметная область:**
- Ассистент: название, описание, категория, модель (строка, например `gpt-4o-mini`), **системный промпт**, пример пользовательского промпта, флаг активности.
- **Запуск (AssistantRun)**: assistantId, userId, промпт пользователя, ответ, статус, ошибка, дата.
- Статусы запуска: `pending` → `success` | `failed`. `pending` нужен в модели даже при синхронной реализации.

**Роли:** admin (категории, ассистенты, все запуски, вкл/выкл) и user (каталог, фильтр, поиск, запуск, своя история).

**Правила бэкенда:**
- JWT с `user_id` и `role`. Права проверяются **централизованно** (middleware). `user_id` берётся из токена, а не из тела запроса.
- `/dummyLogin` выдаёт **фиксированный UUID на роль**, чтобы проверяющий мог воспроизвести сценарий.
- Каждый запуск сохраняется **всегда**, даже при ошибке LLM. При ошибке, таймауте или невалидном ответе — статус `failed` и понятная ошибка в API.
- **Системный промпт живёт только на бэкенде**: фронт шлёт только пользовательский ввод. Если промпт скрыт от пользователя, API не должен его отдавать.
- Нельзя запустить неактивного ассистента; нельзя создать ассистента без промпта или с несуществующей категорией.
- `GET /_info` → 200 (healthcheck).

**LLM:**
- Реальный LLM не нужен для запуска и проверки. Мок-провайдер **детерминированный**.
- Запрос собирается из системного промпта, модели и ввода пользователя. В БД сохраняются промпт, ответ, модель, статус, ошибка.
- В README: пример итогового запроса к LLM, обработка таймаута, невалидного и пустого ответа, ошибки провайдера; как переключиться на OpenAI-совместимый API (фича-флаг или env, без обязательного ключа).
- Usecase зависит от **интерфейса `LLMProvider`**, а не от `MockProvider`. Интерфейс объявляется на стороне потребителя.

**Фронтенд:** React 18 SPA; отдельный слой API; единое хранилище токена и роли; защита роутов по роли (в том числе при ручном вводе URL); loading / error / empty на каждой странице; фильтры синхронизированы с query-параметрами; после действий данные обновляются. Выбор state-менеджера обосновать в README.

**Тесты:** юнит-тесты на бизнес-логику; E2E `admin создал категорию → создал ассистента → user запустил`; тест фильтра; тест «нельзя запустить неактивного»; минимум 3 теста на фронте; анализ coverage в README.

**Запуск:** `docker-compose up --build` из корня; у всех env есть дефолты; бэкенд на 8080, фронт на 3000 (или указан в README); healthchecks; multi-stage Dockerfile; версии Go в `go.mod` и Dockerfile совпадают.

**Доп. задания (дают преимущество):** регистрация по email и паролю (bcrypt), TypeScript, OpenAI-совместимый провайдер за флагом, **стриминг ответа**, адаптивность, теги, избранное, **лайк / дизлайк ответа**, тёмная тема, Swagger, CI в GitHub Actions с coverage, нагрузочный тест, конфиги линтеров.

**Что оценивают:** бизнес-логику, работу с БД и историей, соответствие API, структуру бэкенда, качество React (роутинг, состояние, ошибки), тесты, README и обоснование решений, **качество мок-LLM-интеграции**.

### API-контракт задания (`api.yaml`, OpenAPI) — выжимка

Оригинал: [api.yaml](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/Backend/Fullstack-trainee-assignment-spring-2026/api.yaml). Сервер `http://localhost:8080`, авторизация `Authorization: Bearer <JWT>`, все id — UUID, даты — date-time.

**Единый формат ошибки:**
```json
{ "error": { "code": "ASSISTANT_INACTIVE", "message": "понятный текст" } }
```
Коды: `INVALID_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CATEGORY_NOT_FOUND`, `ASSISTANT_NOT_FOUND`, `ASSISTANT_INACTIVE`, `LLM_PROVIDER_ERROR`, `INTERNAL_ERROR`.

**Пагинация:** запрос `page` (≥1, по умолчанию 1) и `pageSize` (1–100, по умолчанию 10 или 20); ответ — `{ <items>: [...], pagination: { page, pageSize, total } }`.

| Метод и путь | Кто | Ответы |
|---|---|---|
| `GET /_info` | все | 200 |
| `POST /dummyLogin` `{role}` | все | 200 `{token, user}`, 400 |
| `GET /categories` | авторизованные | 200 `{categories}`, 401 |
| `POST /categories` `{name, description?}` | admin | 201, 403 |
| `GET /assistants?categoryId&q&includeInactive&page&pageSize` | авторизованные | 200 `{assistants, pagination}`, 401 |
| `POST /assistants` | admin | 201, 400, 403 |
| `GET /assistants/{id}` | авторизованные | 200, 404 |
| `PUT /assistants/{id}` (все поля, включая `isActive`) | admin | 200, 403, 404 |
| `POST /assistants/{id}/run` `{userPrompt}` | авторизованные | **201** `AssistantRun`, 400, **409** (ассистент выключен), **502** (ошибка LLM-провайдера) |
| `GET /runs/my?status&page&pageSize` | авторизованные | 200 `{runs, pagination}` |
| `GET /admin/runs?assistantId&status&page&pageSize` | admin | 200, 403 |

**Схемы:**
- `Assistant`: id, categoryId, categoryName, name, description, model, `systemPrompt` (*«может быть скрыт от обычного пользователя»*), exampleUserPrompt, isActive, createdAt, updatedAt.
- `AssistantRun`: id, assistantId, assistantName, categoryId, categoryName, userId, model, userPrompt, output, `status` (`pending|success|failed`), error, createdAt.
- Денормализованные имена (`categoryName`, `assistantName`) в ответах избавляют фронт от лишних запросов.

> Для нас: формат `{error:{code,message}}`, коды 409 / 502 для бизнес-отказа и сбоя LLM, `run` с историей — готовый шаблон для API чата AI-buddy (сообщение → запуск агента → статус).

## Frontend весна 2026 «AI-ассистент для улучшения объявлений»

Второе AI-задание Авито — уже со стороны фронтенда. Личный кабинет продавца: список, просмотр и редактирование объявлений.
- Стек обязателен: React 18+, TypeScript, react-router-dom; UI-библиотека и стейт-менеджер (в списке прямо назван **Zustand**) и **TanStack Query** — на выбор.
- **AI-функции на форме:** «Придумать / Улучшить описание» (LLM предлагает текст, его можно подставить) и «Узнать рыночную цену».
- **LLM:** реализовать самому. Варианты — **локально через Ollama** (`ollama pull llama3`, `POST http://localhost:11434/api/generate`, бесплатно и без интернета) или внешний API с ключом в `.env`. «Приватные токены не должны оказаться в общем доступе».
- Состояния загрузки и ошибок — «неотъемлемая часть каждой страницы». Черновик формы — в localStorage.
- Со звёздочкой: **чат с AI внутри карточки** (контекст объявления передаётся автоматически, история видна), **сравнение «было → стало»** с подсветкой правок, тёмная тема, docker compose, отмена запросов при уходе со страницы, юнит-тесты.
- ИИ при разработке разрешён, но на интервью могут попросить объяснить код.

> Для нас: Ollama — хороший **третий вариант провайдера** (кроме мока и внешнего API). Жюри может запустить бота локально без ключа. «Было → стало» и чат с автоконтекстом — готовые UX-паттерны.

## Frontend осень 2026 «Бронирование переговорок» — правила домена

Полезно как образец **имитации корпоративного сервиса** (календарь и переговорки) для инструментов бота:
- Офис обязателен; бронь только на будущее; рабочие часы 09:00–20:00 по местному времени; минимум 15 минут, шаг 15 минут; не дальше 30 дней вперёд.
- Брони одной комнаты не пересекаются; отменить можно **только свою будущую** бронь.
- **Бэкенд — источник истины** и перепроверяет все ограничения; клиент обрабатывает **409 (конфликт)**.
- Real-time через WebSocket или SSE; со звёздочкой — переподключение с ресинхронизацией, оптимистическая отмена с откатом, экспорт `.ics`, повторяющиеся брони.

## Чек-лист ревьюера Авито — фронтенд (сводно по 4 разборам 2024–2025)

### Запуск, README, git
- README: описание, запуск (в том числе Docker), стек, архитектура, особенности реализации. Кратко, конкретно, в Markdown.
- Сверься с ТЗ: все функции реализованы, маршруты точно как в задании (например, `/board/:id`).
- Проверь фичи **на живом сайте**, а не только в коде.
- Чистая история коммитов: «одна подзадача — один коммит».
- В консоли нет `console.log`, warning и error: примерно у 80% кандидатов там мусор, а логи могут содержать приватные данные.

### Архитектура и код
- Выбери архитектуру (например, FSD для крупных проектов), обоснуй и опиши в README или `ARCHITECTURE.md`.
- `App.tsx` — только роутинг; логика — на страницах и в хуках.
- В компоненте сначала данные, потом обработка, потом отрисовка. Компонент длиннее ~150 строк — дробить. Логику — в кастомные хуки, чистые функции — в `utils`, константы — рядом (`constants.ts`) или в `src/constants`.
- Осмысленные имена (`TaskFormPopup`, а не `Popup`).
- Named exports; баррели `index.ts` для `components` и `hooks`, без циклов (`import/no-cycle`); сортировка импортов (`import/order`), `import type` отдельно.
- Без инлайн-стилей `style={}` (кроме обоснованных случаев).
- Условия не больше 2–3 операндов — выделяй логические группы. Маппинги `Record<Enum, string>` вместо цепочек `if`.
- Унифицируй разнотипные данные бэкенда в одну UI-модель (пример: `Listing` + `transformListings`).
- TypeScript — «золотой стандарт». ESLint + Prettier с первого дня. Зависимости разработки — в `devDependencies`.
- Сторонние библиотеки — да, но без перебора.

### Данные и запросы
- Состояние: сначала встроенные `useState` / `useReducer`, глобальный store — по необходимости.
- Формы: валидация через **zod**; черновик в localStorage с троттлингом; одна форма для создания и редактирования.
- Не слать лишних запросов: debounce или блокировка кнопки; проверяй вкладку Network. Не делай последовательных запросов, если можно параллельно.
- **Отмена запросов** при уходе со страницы (против race conditions).
- Поиск: debounce с очисткой таймера, порог от ~3 символов, история поиска.
- Адрес API и ключи — через переменные окружения, не в коде.

### UX-состояния
- **Лоадеры, ошибки и пустые состояния** везде; блок ошибки предлагает действие (например, «повторить»).
- **Error Boundary**: один переиспользуемый с разными `fallback`, вокруг страниц и форм; логирует ошибку; покрыт тестом.
- Ховеры и курсор-«рука» на интерактивных элементах; раскрывашки для длинного текста; видимые скроллы; fallback-картинки; адаптив; кнопка «наверх».
- Фильтры: чекбоксы для мультивыбора, select или radio для одного, слайдер для диапазона, switch для булева. Состояние фильтров — в query-параметрах.
- Виртуализация списков — только для больших (больше ~50 элементов; проверить на 1 000).
- Следи за Core Web Vitals.

### Тесты
- Утилиты — крайние случаи (пустые данные, ошибки парсинга). Компоненты — рендер и взаимодействие. Store — редьюсеры и селекторы.
- Мокать внешнее: localStorage, API, store. Специально «ломать» код, чтобы проверить, что тесты падают.

### Частые ошибки в коде (разбор 2024)
- Таймер debounce создаётся на каждый ввод без очистки.
- Нет `key` в списках; список не в `<ul>`.
- Лишняя работа с данными, которые не нужны.
- `let` вместо `const` для значений из хуков.
- Длинные относительные импорты вместо баррелей и абсолютных путей.

## Чек-лист ревьюера Авито (сводно по разборам 2024–2025)

Собрано из «Solution and advice» для весны 2024, осени 2024, зимы 2025 и весны 2025.

### Запуск и README
- Проект поднимается «с нуля» одной командой: миграции проходят, сервис стартует, API отвечает. Проверь чистый старт перед сдачей.
- В README: как запустить, какие вопросы возникли и какие допущения сделаны, схема БД, принятые решения.
- Строго соблюдай формат ответа из спецификации (`Content-Type`, коды, тело).

### Code style и структура
- Автоформат и линтер (`gofmt` / `goimports`, `golangci-lint`, pre-commit hook). Конфиг линтера лежит в репозитории.
- Обработчики разложены по доменам, а не в одном `handlers.go`.
- Моки — отдельно от прод-кода (`mocks/`, генерация через `mockery`).
- Именованные DTO и доменные модели вместо анонимных `struct{}`.
- Без пакета-свалки `utils`; используй функции стандартной библиотеки, а не велосипеды.
- `TODO` — только со ссылкой на задачу в трекере.

### Архитектура и слои
- Handler — парсинг, валидация входа, маппинг ошибок в HTTP. **Usecase / service** — вся бизнес-логика. **Repository** — только доступ к данным, SQL не протекает наружу.
- Интерфейсы объявляются у потребителя; зависимость — от интерфейса.
- Интерфейсы «тонкие», по доменам (`UserRepository`, `ProductRepository`), а не один огромный.
- Graceful shutdown.

### Данные и БД
- Миграции — отдельными файлами (`0001_…`, `0002_…`) через инструмент вроде `golang-migrate`, а не одним `init.sql`.
- **Бизнес-правила валидируются в приложении**, а не CHECK-констрейнтами в БД. БД отвечает только за целостность: `NOT NULL`, внешние ключи.
- Справочники (`status`, `type`, `city`) — отдельные таблицы с integer id, а не строки и не `ENUM`.
- Индексы — под фильтры, внешние ключи, сортировку и пагинацию; составные — под сложные фильтры. Проверять через `EXPLAIN ANALYZE`; лишних индексов не делать.
- Транзакции — только там, где нужна атомарность нескольких изменений, через transaction manager; не оборачивать всё подряд.
- Защита от гонок при конкурентных изменениях: атомарные операции, блокировки.
- Динамические запросы — через билдер, а не склейкой строк.

### Тесты
- Тестируй **бизнес-логику**: переходы статусов, расчёты, ошибки, граничные условия. Тесты одной инфраструктуры дают ложное чувство защиты.
- Покрытие ниже ~70% считается слабым. (Наш кейс требует > 80%.)
- E2E и интеграционные тесты — на отдельной тестовой БД (`docker-compose.e2e.yaml`).
- Без flaky-тестов: не зависеть от порядка в map, текущего времени без фиксированных часов и общей БД.

### Безопасность и конфигурация
- `.env` — в `.gitignore`; в репозитории только `.env.example`. Секреты — из env или Vault.
- Пароли — только хешами (bcrypt).
- JWT — в стандартном заголовке `Authorization: Bearer <token>`.
- Проверяй права на конкретную сущность (пользователь A не меняет объект пользователя B), а не только роль.
- Пользователь **не видит внутренние ошибки** — только понятное сообщение; подробности уходят в лог.

### Логирование
- Ошибки логируются, а не глотаются (Zap или slog). Пароли и токены в лог не пишутся.
- Ошибки сравниваются через `errors.Is()`.

### Типичные баги в бизнес-логике
- Не проверено «отправитель ≠ получатель» — можно накрутить монеты.
- Неатомарные операции: списание и зачисление без транзакции.
