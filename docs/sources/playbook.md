## Миссия и ценности

Миссия: помочь каждому улучшить свою жизнь и жизнь людей вокруг. Пять ценностей:

1. Всё начинается с потребностей пользователей.
2. Решай быстро и аргументированно: данные плюс опыт и логика, без аналитического паралича.
3. Упрощай: из нескольких решений выбирай более простое, неизбежную сложность прячь под капот.
4. Вместе мы можем больше: проси помощи у соседних команд и помогай сам.
5. Главное — результат: цели в количественных метриках; оценивают по достигнутому, а не по усилиям.

## Структура

- Структура горизонтальная. Разработка состоит из **юнитов** — кросс-функциональных команд (бэкенд, фронтенд, мобильные, QA, дизайнер, продакт, аналитик).
- Юниты объединены в **кластеры**: платформенные (архитектура, инфраструктура) и продуктовые (Buyer Experience, Seller Experience).
- Разработкой руководят CTO и **TMG** (Tech Managers Group) — руководители кластеров.
- **Unit-Leader** отвечает за стратегию и OKR юнита, коммуникации и команду. Он работает как тренер и наставник, а не как диктатор.
- Перейти в другой юнит можно; каждый случай разбирают отдельно.

> Для бота: в чек-листе есть «пространство своего кластера / команды», а орг-модель «кластер → юнит» отсюда. Её можно взять для синтетической оргструктуры.

## SPT — работа с обращениями пользователей

- SPT — короткое имя проекта Support в Jira, отдельный процесс для обращений пользователей.
- Источники: HelpDesk (главный), соцсети, магазины приложений, клиентские менеджеры.
- Три типа задач: **Bug**, **Crash** (падение iOS / Android-приложения) и **Feature** (запрос функции; сюда же «багофичи» — обращения, которые завели как баг, но ошибки нет).
- Поток: обращение → тикет-инцидент в HelpDesk → агент заводит тикет-проблему, который объединяет одинаковые инциденты → SPT-координатор заводит задачу в Jira SPT и назначает её на юнит.
- Пять приоритетов: P0 Blocker, P1 Critical, P2 Major, P3 Normal, P4 Minor. Приоритет задаёт матрица «частота × серьёзность»:

| Частота \ серьёзность | Crash | Failure | Flaw | Annoyance |
|---|---|---|---|---|
| Всегда | P0 | P0 | P2 | P3 |
| Иногда | P1 | P1 | P3 | P4 |
| Редко | P2 | P2 | P4 | P4 |

- Ещё учитывают число обращений, жалобы крупных и средних бизнес-клиентов и лишнюю нагрузку на поддержку.
- Команда, получившая задачу, меняет статус, ставит приоритет и описывает временное решение для пользователя (или пишет, что его нет). Если чинить не будут — пишет причину.
- Задачу закрывают только после того, как фикс уже в проде.
- Для SPT есть свой дашборд метрик; команды разбирают корневые причины.

## Принципы разработки

**Основные:**
- Команда сама отвечает за работоспособность своей системы во всех окружениях, а не только в проде.
- Система — это ответственность надолго: её поддерживают до последнего потребителя и чинят уязвимости даже в старых сервисах.
- Сначала проектирование с учётом текущей архитектуры. Не заводить сервис под каждую фичу, избегать распределённых транзакций.
- Избегать ненужной сложности и дублирования (DRY).
- Сначала искать готовые решения, а не изобретать велосипед.
- Уважать чужой код: большие изменения обсуждать с владельцем, код-ревью делать быстро и с понятными комментариями.
- Ненужное удалять: код, сервисы, базы.

**Проектирование и интерфейсы:**
- Избегать жёсткой связанности: не ходить в чужую БД или кэш, интегрироваться через события в шине данных, а не через синхронные вызовы N сервисов.
- Не завязываться на детали реализации чужих систем.
- Сначала продумать внешний интерфейс. Обратную совместимость держать, пока у интерфейса есть хоть один клиент. Несовместимое изменение — только новой версией.
- Интерфейсы должны быть простыми, чтобы клиент интегрировался быстро.

**Документация:** интерфейсы, особенности и нефункциональные требования описаны и актуальны, чтобы новичок быстро вошёл в курс дела.

**Данные:**
- Никакой бизнес-логики в хранимых процедурах.
- Шина данных — только для уведомлений о событиях, а не для передачи состояния.
- Кэшировать можно и нужно, но помнить об инвалидации.
- У данных один источник правды.
- Сервисы stateless: никакого состояния на диске.
- Миграции обратно совместимы: старая и новая версия сервиса работают с обеими схемами.

**Взаимодействие сервисов:**
- Где можно — асинхронно.
- **Fault tolerance:** если зависимость упала, сервис деградирует мягко — не рисует блок, отдаёт заглушку, пишет метрику.
- Запрашивать только нужные поля.

**Тестирование:**
- Любое изменение должно легко проверяться автотестами; если нельзя — переделать реализацию.
- «Что не протестировано — не работает; что не работает — не катим».
- **Zero Bug Policy (ZBP):** баги не копят. По каждому сразу решают — чинить сейчас, в очереди или никогда (закрыть); не-баг превращают в задачу.

**Эксплуатация:** разработчик знает свой сервис, настраивает дашборды и алерты и всегда может сказать, всё ли с ним в порядке.

> Для AI-buddy это прямые требования к нашему коду: fault tolerance при сбое LLM и сервисов, обратная совместимость API, тесты на каждое изменение, метрики.

## Соседское соглашение (изменения в чужом коде)

Цель — меньше багов и меньше накладных расходов на общение, когда один юнит меняет код другого. Ключевые правила:

- Правило бойскаута: оставь код лучше, чем он был.
- PR можно делать в любой репозиторий, если это не запрещено политиками безопасности.
- В чужом коде действуют Coding Standard и правила ревью команды-владельца. Без согласия владельца не мёржить.
- Новый код — вместе с тестами. Если сломал логику, а тесты зелёные — тесты нужно исправить.
- Кто сломал (тесты, метрики, логирование), тот и чинит.
- Отклоняешь PR — объясни почему.
- Код-ревью — не позже следующего дня.
- Используешь чужое API — напиши тест на него.
- Владеешь репозиторием — отвечаешь за его тесты, метрики и логи.
- Принцип «Keep Going Green»: сборки и тесты всегда зелёные. Покрытие при расширении функционала не должно падать. Владелец держит покрытие в районе 50–80%.
- Об изменениях владельцев оповещает **COP** (Code Ownership Plugin).

## Инженерные практики

### Live Site Review (LSR) — разбор инцидентов

- Как замечают проблемы: Grafana (общий дашборд пользовательских событий), канал в Slack, синтетический мониторинг, алерты сервисов.
- Порядок: дежурные видят проблему → чинят сами или зовут команду → автоматика заводит **Auto LSR** в Jira (длительность, функциональность, потерянная выручка) и отмечает критичность → заводят постмортем-тикет → встреча-разбор → action items → закрытие и запись в базу знаний.
- Команда **«Мониторинг 24/7»** первой тушит пожар.
- Поля постмортема: Summary, Description, Priority (Critical / Major / Normal / Minor), ссылка на Slack, команда-виновник, пострадавшие сервисы, участники, повторялось ли раньше, вероятность повтора, action items, ссылка на HelpDesk, число обращений (HD count), длительность.
- Хороший action item — конкретная задача или проект (не процесс), с ответственным и сроком, выполнимая за полгода. Плохой — «лучше тестировать».
- Лучшие постмортемы раз в две недели публикуют в общем канале как «стенгазету».

### Архитектурный комитет

- Около 40 экспертов, ревьюят архитектуру по заявкам, не чаще 2 раз в неделю.
- Идти туда нужно, если: выносите сервис из монолита на критичном пути; делаете платформенное решение для других юнитов; делаете высоконагруженный сервис (>500 rps или >100 тяжёлых запросов в секунду, сложные данные или масштабирование, много внешних зависимостей).
- Подготовка: описать решение по чек-листу, разослать приглашение стейкхолдерам, за 2 рабочих дня скинуть слайды в канал, назначить отдельного человека записывать фидбэк.
- После встречи — выводы и план. Если комитет не пройден — доработка и повторная встреча.

## Tech Design Review (TDR)

- Описать изменение в дизайн-документе и собрать отзывы коллег — похоже на ревью PR.
- Цикл: проблема → дашборд TDR → дизайн-документ → ревью → оценки → доработка.
- Когда нужен: продукт в портфеле (до Gate 2); решение затрагивает больше одного юнита; работы больше 3 человеко-месяцев; растёт техдолг; сервис передают другой команде; внедряют новую технологию.
- Шаблон: проблема, описание, схема зависимостей, компромиссы, альтернативы, FAQ, нагрузка (RPM, реплики на DC, соотношение чтения и записи), ресурсы (БД, ceph, GPU, файлы), структура БД, ИБ (публичное API? ПДн?), метрики.

> Для нас TDR похож на наш `design.md` в OpenSpec и ADR. На защите можно сказать, что процесс сделан «как в Авито».

## Платформа Avito PaaS

- Платформа для разработки и эксплуатации сервисов, чтобы разработчики писали бизнес-логику, а не возились с инфраструктурой.
- Интерфейсы: консольная утилита `avito` (в чек-листе — «avito-cli») и **PaaS-дашборд**.
- Даёт интеграцию с БД, структурированные логи и метрики, работу с секретами, очереди, шину данных, live reload, запуск тестов. Не нужно писать прокси, клиенты сервисов и Helm-конфиги.
- Зачем Авито: быстрее TTM, инфраструктурные фичи сразу на всю компанию, обновления без участия разработчиков, стабильность.
- Подробнее: статья на Хабре [«Платформа как сервис в Авито»](https://habr.com/ru/company/avito/blog/527400/).

## OKR и Performance Review

- **OKR** ставят на уровне юнитов. Источники — стратегия компании, цели юнита, бэклог проблем. Формального утверждения нет; есть «согласование» с соседями.
- **Performance management**: постановка целей (OKR, бывают индивидуальные и личные цели развития), оценка (**Performance Review** в инструменте «Перфоратор»), разговор об итогах.
- Performance Review проходит раз в полгода (апрель и октябрь), письменно, влияет на премию.
- Роли: сотрудник (пишет self-review), респонденты (менеджер, заказчики, коллеги, подчинённые), менеджер.
- Этапы: self-review → менеджер одобряет список респондентов → отзывы → калибровка и рейтинг → встреча по итогам.

## Профили инженеров (E1–E8)

- С осени 2021 года уровни Intern / Junior / Middle / Senior / Lead заменили на **E1–E8**. Два трека — IC и менеджерский.
- Каждый уровень описан по блокам: экспертность, инженерная культура, ответственность за результат, ориентация на бизнес, Agile Mindset, коммуникация, развитие себя и других. Ожидания накапливаются: E4 умеет всё, что E1–E3.
- Для выбора вектора роста инженер с тимлидом составляют **Windrose навыков**.

**E1 — уровень стажёра (кратко):**
- Задачи из бэклога на 1–2 дня, полностью декомпозированные, работа под присмотром наставника, неважная функциональность.
- Риски не оценивает сам — зовёт наставника; сообщает, если не успевает.
- Учится лучшим практикам у наставника, вручную проверяет «зелёные» сценарии.
- Сроки и результат согласует с наставником; соблюдает DoR и DoD команды; признаёт ошибки.
- Получает от наставника **роадмап обучения с чек-пойнтами** и идёт по нему вместе с ним.

**E2:**
- Задачи на 1–2 дня с подробным объяснением; декомпозирует и пишет код в основном сам.
- Важная функциональность — под присмотром.
- Применяет KISS и DRY, смотрит мониторинги в проде.
- Выясняет ценность задачи, не замалчивает проблемы, спокойно решает конфликты.
- Вместе с бадди или руководителем составляет план развития с чек-пойнтами.

> Для бота: «роадмап с чек-пойнтами» и «план развития с бадди» — это ровно то, что показывает панель «мой онбординг». Ожидания E1 — хорошая база для критериев успеха стажировки.

**Кто по профилям отвечает за онбординг** (роли для нашей модели прав):
- **E3** — сам двигается по плану развития, уже без напоминаний менеджера или бадди.
- **E4** — «занимается онбордингом новичков», терпелив к тем, кто знает меньше, проводит техинтервью. Типичный уровень **бадди / наставника**.
- **M1 Tech Lead** — **организует процесс онбординга** и **ставит новичку цели на испытательный срок**; проводит 1:1 и performance review. Это наша роль **«руководитель»**.
- Тимлиды уровнем выше бывают бадди для руководителей соседних команд — то есть «бадди» в Авито бывает не только у стажёров.
- В дизайне: руководитель вовлекает в онбординг всю команду нового сотрудника. В DS: старшие отвечают за рост коллег уровня стажёра.

## Найм, обучение, студентам

- **Найм инженеров:** скоринговое интервью → техническое (секции для backend, frontend, mobile и QA) → финальное → оффер.
- **Стажировки:** несколько раз в год, в технический департамент, от 6 месяцев до года, боевые задачи; большинство стажёров остаются в штате. Направления: Frontend, Backend, iOS, Android, QA, а также аналитика (BI, DS). Ещё есть Академия аналитиков и магистратура МАИ по высоконагруженным системам.
- **Обучение:** личный бюджет на развитие после испытательного срока (конференции, курсы, книги, английский); публичные и внутренние митапы (еженедельный Tech Meetup); ежеквартальный хакатон AvitoHack; тренинги по hard и soft skills, в том числе **Tech Onboarding**; Авито Академия и MyAcademy; библиотека МИФ.
- **Книги** ([books.md](https://github.com/avito-tech/playbook/blob/master/books.md)): большой список по направлениям — продукт, менеджмент, алгоритмы, паттерны, микросервисы, Linux, Go (Effective Go, Go CodeReview Comments, Донован и Керниган), Python, C, БД, архитектура (Клеппман, SRE), QA. Книги из Backend-чек-листа есть здесь.

## Что взять в AI-buddy

1. **Базу знаний для Q&A**: ответы на «что такое SPT / ZBP / PaaS / LSR / TDR / OKR / E1», с цитатой источника и пометкой «по открытому Playbook Авито».
2. **Оргмодель для моков**: кластер → юнит → роли (unit-lead, бэкенд, QA, дизайнер, продакт) плюс бадди и куратор стажировки.
3. **Набор имитаций сервисов**: мессенджер, трекер задач (Jira-like, с типами Bug / Crash / Feature и приоритетами P0–P4), вики, календарь, дашборд (Grafana-like).
4. **Критерии прогресса стажёра**: ожидания уровня E1 плюс чек-лист.
5. **Инженерные правила для нашего кода**: fault tolerance, тесты, обратная совместимость, ZBP.
