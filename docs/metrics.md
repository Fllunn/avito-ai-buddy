# Метрики пользы и проверка эффекта

> Кейс требует предложить метрики пользы и способ проверить эффект на стажёрах. Базовые цифры — от организаторов ([organizers-qa.md](sources/organizers-qa.md)); сценарии — [docs/scenarios/](scenarios/README.md).

## Цель

Сократить рутинные организационные обращения к наставнику и ускорить выход стажёра на самостоятельные задачи, не подменяя содержательную работу наставника.

## Базовая линия (данные организаторов, приблизительно)

| Показатель | Сейчас | Чем AI-buddy может на него влиять |
|---|---|---|
| Время наставника в первые 2–3 месяца | ~5 ч/нед | организационные вопросы и доступы уходят в чат и сервисы |
| Время наставника после адаптации | ~2–3 ч/нед | не цель прототипа: там 1:1, ревью, развитие |
| Время до первой самостоятельной задачи | ~2 недели | доступы и ориентирование не задерживают старт |
| Длительность адаптации | ~2 месяца | период пилота |
| Удовлетворённость онбордингом | 9/10 | не должна снизиться |
| Удовлетворённость чек-листом | 68% | план с владельцами и статусами заменяет статичный чек-лист — главный кандидат на рост |
| Удовлетворённость наставником | 90% | не должна снизиться: агент не заменяет наставника |

Самая частая тема вопросов к наставнику — организационная: доступы, оборудование, документы. Сценарий доступа нацелен прямо на неё.

Цифры получены разными способами: ~5 ч/нед за первые 2–3 месяца — это 40–60 ч, а общая оценка из кейса — 40–48 ч за 6-месячную программу. Для сравнения берём недельную оценку, а точную базу снимаем в пилоте на старте.

## Метрики

### Польза для наставника

| Код | Метрика | Как считать | Источник |
|---|---|---|---|
| U-1 | Время наставника на организационные темы, ч/нед | самоотчёт наставника раз в неделю (доступы, оборудование, документы, «что дальше») | короткий опрос в пилоте |
| U-2 | Доля организационных вопросов стажёра, закрытых без человека | технический прокси: вопросы с источником или сохранённым результатом без эскалации / все организационные вопросы; решение вопроса проверяется в пилоте | события агента |
| U-3 | Эскалации к людям по темам | число ответов «к кому идти» по темам: наставник, руководитель, куратор | события агента |

### Польза для стажёра

| Код | Метрика | Как считать | Источник |
|---|---|---|---|
| S-1 | Время до первой самостоятельной задачи | дата старта → дата первой задачи, взятой без наставника | опрос стажёра и наставника |
| S-2 | Время до доступа в пространство команды | первое обращение по доступу → статус «Одобрена» | события + сервис заявок |
| S-3 | Шаги 1–2 недели, закрытые в срок | шаги стажёра в состоянии «выполнен» до конца периода / все шаги стажёра периода | план |
| S-4 | Удовлетворённость чек-листом / планом | тот же вопрос, что в текущем опросе (68%) | опрос в конце адаптации |
| S-5 | Удовлетворённость онбордингом и наставником | те же вопросы (9/10, 90%) | опрос в конце адаптации |

### Качество агента

| Код | Метрика | Как считать |
|---|---|---|
| Q-1 | Доля действий с подтверждённым исходом | уникальные attempt_id с последним исходом «успех» или «отказ» / все уникальные подтверждённые попытки; успех после сверки учитывается один раз |
| Q-2 | Доля ответов по материалам со ссылкой | ответы с источником / все ответы на вопросы по материалам |
| Q-3 | Доля честных «инструкции нет» | ответы без источника с указанием ответственного; рост по теме — сигнал, что не хватает материала |
| Q-4 | Отмены и правки карточек | отменённые и изменённые карточки / показанные; рост — вопросы агента непонятны или параметры угаданы неверно |
| Q-5 | Оценка ответов (backlog) | Вне реализации и приёмки этого change; отдельный сценарий N-13 |
| Q-6 | Нарушения прав | закрытые данные в ответе или контексте LLM; цель — 0, проверяется тестами и выборочным аудитом |

### Технические

| Код | Метрика | Требование |
|---|---|---|
| T-1 | Время ответа локальных операций (план, статусы, карточки), p95 | < 1 с — требование кейса |
| T-2 | Время ответа LLM, p95; доля таймаутов LLM | значения фиксируются при выборе модели |
| T-3 | Доля сбоев и таймаутов сервисов-имитаций | в демо задаётся панелью имитации |

## События аналитики

События пишутся в стиле Clickstream. **Без текста сообщений и без ПДн**: только идентификаторы, коды и длительности.

Общие поля: уникальный `event_id`, `ts`, `user_id` (синтетический), `role`, `team`, `period`, `scenario`, `session_id` (аналитический идентификатор, не секрет cookie).

События дедуплицируются по event_id и записываются транзакционно с результатом. В исходе попытки сохраняется attempt_id; Q-1 считается по последнему подтверждённому исходу, а не сумме промежуточных событий. Тексты, обоснования и тела внешних ошибок запрещены. `feedback_given` и Q-5 остаются в backlog; технические прокси не доказывают экономию часов наставника.

| Событие | Дополнительные поля |
|---|---|
| `chat_message_sent` | `source` (кнопка / текст) |
| `intent_classified` | `intent`, `confidence_bucket`, `llm_ok` |
| `clarification_asked` | `slot` (ресурс, уровень, даты, задача), `attempt_no` |
| `answer_shown` | `kind` (шаг / материал / к кому идти / вне рамок), `has_source`, `doc_ids`, `latency_ms` |
| `card_shown` / `card_edited` / `card_cancelled` / `card_expired` | `card_id`, `card_type`, `version`, `edit_via` (поле / чат) |
| `card_confirmed` | `card_id`, `version` |
| `permission_denied` | `stage` (до карточки / при подтверждении), `object_type` |
| `attempt_started` / `attempt_outcome` | `attempt_id`, `service`, `outcome` (успех / отказ / недоступен / таймаут / сбой сохранения), `latency_ms` |
| `reconciliation_result` | `attempt_id`, `result` (найдена / не создана / ручная проверка), `checks` |
| `status_changed` | `object_type`, `from`, `to` |
| `step_marked` | `step_id`, `action` (выполнен / вернуть в работу) |
| `llm_error` | `kind` (таймаут / ошибка), `stage` |


## Как проверить эффект

1. **На хакатоне — работоспособность.** Все три сценария проходят от реплики до результата; исходы, отказы в правах и неизвестный исход воспроизводятся по сидам; T-1 измеряется автотестами.
2. **Юзабилити-тест на 5–8 участниках** с одинаковыми заданиями на синтетических данных: «узнай следующий шаг», «получи доступ в пространство команды», «оформи отгул и отмени его». Фиксируем время до правильного шага, долю заданий без подсказки, ошибки чтения статусов («заявка создана» ≠ «доступ выдан»). Такой тест найдёт проблемы интерфейса, но не докажет экономию времени наставника.
3. **Пилот после хакатона.** Сопоставимые группы стажёров: с AI-buddy и без, в похожих командах и одном наборе. Длительность — период адаптации (~2 месяца). Гипотезы:
   - H1: время наставника на организационные темы (U-1) ниже, чем в контрольной группе;
   - H2: доступ в пространство команды (S-2) появляется быстрее;
   - H3: удовлетворённость чек-листом / планом (S-4) выше 68%, а удовлетворённость онбордингом и наставником (S-5) не ниже текущих.
   Пороги успеха согласуются с командой адаптации до старта пилота. Экономия часов не заявляется без измерений.
