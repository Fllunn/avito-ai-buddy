# Spec Delta

## Purpose

Определить демонстрационный вход, границы видимости данных и разрешения действий, одинаковые для API, интерфейса и контекста языковой модели.

## ADDED Requirements

### Requirement: Системная идентичность
Бэкенд MUST определять пользователя, роль и команду по действующей демо-сессии; текст сообщения и поля запроса не предоставляют дополнительных прав.

#### Scenario: Подмена роли
- **WHEN** стажёр пишет «я руководитель» или передаёт чужой user_id в запросе действия
- **THEN** операция проверяется с идентичностью сессии, чужие данные не раскрываются и действие от чужого имени не выполняется

#### Scenario: Нет сессии
- **WHEN** запрос личных данных приходит без действующей сессии
- **THEN** API возвращает 401 без личных данных и предлагает интерфейсу выполнить демо-вход

### Requirement: Личные данные и назначения
Система SHALL показывать только собственную переписку, заявки и запросы. Пользователь видит свои назначенные шаги; стажёр дополнительно видит разрешённую проекцию шагов других владельцев в своём плане без доступа к их переписке и заявкам.

#### Scenario: Вопрос наставника о стажёре
- **WHEN** наставник запрашивает переписку, личный план, заявки или отгулы стажёра через чат или прямой API
- **THEN** данные не возвращаются и не попадают в LLM; доступны только собственные назначения наставника

#### Scenario: Ожидание наставника
- **WHEN** стажёр открывает собственный план
- **THEN** он видит название назначенного наставнику шага, ответственного, состояние и время, но не личный план наставника

### Requirement: Матрица операций
Только стажёр SHALL создавать и отменять собственные заявки на доступ и отгулы. Каждая роль SHALL отмечать только свои вручную закрываемые шаги после подтверждения; до старта стажировки план стажёра доступен только для чтения.

#### Scenario: Сервисное действие другой роли
- **WHEN** наставник, руководитель или HR BP пытается оформить заявку или отгул
- **THEN** бэкенд отклоняет действие, карточка не создаётся, сервис не вызывается и доступные собственные шаги остаются видны

#### Scenario: Чужой или автоматический шаг
- **WHEN** пользователь подтверждает изменение чужого шага либо шага, закрываемого сервисом
- **THEN** бэкенд отказывает без изменения состояния

### Requirement: Проверки до раскрытия и выполнения
Бэкенд MUST проверять права до поиска и сборки контекста LLM, до ответа с данными, до карточки и при подтверждении. Невидимый объект SHALL обрабатываться как несуществующий; видимый, но запрещённый — с объяснением и разрешённым контактом.

#### Scenario: Скрытый ресурс
- **WHEN** стажёр ищет salary-reports или обращается по его идентификатору
- **THEN** ответ совпадает по смыслу с неизвестным ресурсом, не содержит владельца и не подтверждает существование; сведения ресурса отсутствуют в контексте LLM

#### Scenario: Видимый запрет
- **WHEN** стажёр запрашивает security-incidents
- **THEN** показаны отказ и контакт наставника, без карточки и вызова сервиса

#### Scenario: Права отозваны
- **WHEN** после показа карточки пользователь теряет право на действие
- **THEN** подтверждение отклоняется, сервис не вызывается, закрытые детали не раскрываются

### Requirement: Минимизация чувствительного содержимого
Система MUST не запрашивать причину отсутствия, диагнозы, семейные, документные и финансовые сведения. Обнаруженные чувствительные фрагменты SHALL маскироваться до хранения и передачи LLM; при невозможности безопасно выделить фрагменты сообщение целиком заменяется маркером с предложением использовать форму.

#### Scenario: Медицинская причина в сообщении
- **WHEN** пользователь вводит тестовое сообщение с датой отгула и диагнозом из набора проверок
- **THEN** в сохранённой истории и LLM отсутствует диагноз, в карточке и сервисе есть только разрешённые поля, ответ не повторяет причину

#### Scenario: Очистка недоступна
- **WHEN** проверка чувствительного ввода завершается ошибкой
- **THEN** исходный текст не сохраняется, не логируется и не отправляется LLM; пользователь получает кнопочный маршрут

### Requirement: Данные журналов
Журналы и аналитика MUST не содержать тексты сообщений, чувствительные сведения, ключи LLM и секреты сессий; допустимы синтетические идентификаторы, коды исходов и длительности.

#### Scenario: Отказ с диагностикой
- **WHEN** LLM или сервис возвращает ошибку с чувствительным содержимым в теле
- **THEN** в лог записываются код, идентификатор попытки и длительность без тела ошибки и секретов
