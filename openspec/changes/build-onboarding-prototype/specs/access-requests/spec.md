# Spec Delta

## Purpose

Довести запрос доступа стажёра от разрешённого ресурса до сохранённой заявки и подтверждённого результата согласования через заменяемую имитацию сервиса.

## ADDED Requirements

### Requirement: Выбор и допустимость ресурса
Система SHALL сопоставлять название, код и синонимы только с видимым каталогом. Пространство «моей команды» SHALL определяться из профиля; неоднозначность требует выбора. Запросить можно только разрешённый ресурс и уровень из каталога, совпадающий с уровнями члена команды.

#### Scenario: Ресурс неоднозначен
- **WHEN** стажёр просит «доступ в трекер» при нескольких видимых проектах
- **THEN** он получает варианты с полными именами; карточка не создаётся до выбора

#### Scenario: Недопустимый уровень
- **WHEN** стажёр просит администрирование, отсутствующее в каталоге
- **THEN** показаны допустимые уровни, запрос не отправляется

### Requirement: Проверка существующего доступа
До карточки система MUST проверять выданный доступ, открытые заявки и спорные попытки пользователя на ресурс. Их наличие блокирует новую заявку; недоступность проверки SHALL блокировать создание карточки без догадки о состоянии.

#### Scenario: Открытая заявка
- **WHEN** на ресурс уже есть заявка created или in_review
- **THEN** показаны её номер и статус с действиями проверки и разрешённой отмены; новая не создаётся

#### Scenario: Доступ уже выдан
- **WHEN** доступ уже есть, но ресурс не открывается
- **THEN** показаны сведения о выданном доступе и контакт для проверки, повторная заявка не создаётся

### Requirement: Обоснование и согласующий
Для планового или рекомендованного ресурса система SHALL составлять черновик обоснования из профиля и плана; вне рекомендации — спрашивать задачу и советовать наставника без запрета. Для ресурса «по задаче» объяснение пользователя обязательно. Обоснование SHALL содержать 10–500 символов без чувствительных данных; согласующий берётся из каталога.

#### Scenario: По задаче
- **WHEN** стажёр выбирает launch-plans
- **THEN** система спрашивает задачу, не подменяет её догадкой и без ответа не создаёт карточку

#### Scenario: Несколько уровней
- **WHEN** у ресурса несколько уровней и стажёр не назвал уровень
- **THEN** показан выбор с вариантом по умолчанию первым; «не знаю» выбирает его с явным пояснением

### Requirement: Создание и последствия
Создание SHALL выполняться только после подтверждения актуальной карточки по confirmed-actions. Результат created SHALL означать создание заявки, а approved — выдачу доступа; для пространства своей команды только approved завершает P6 и разблокирует P7.

#### Scenario: Заявка создана
- **WHEN** имитация возвращает created и результат сохранён
- **THEN** номер ACC-…, ресурс, уровень, время и согласующий видны в чате и плане, P6 ожидает согласующего, доступ не объявляется выданным

#### Scenario: Доступ выдан
- **WHEN** подтверждён статус approved для пространства своей команды
- **THEN** P6 выполнен с источником сервиса, P7 доступен, в ленте одно уведомление

#### Scenario: Отказ и повтор
- **WHEN** заявка отклонена
- **THEN** P6 требует внимания, показаны разрешённая причина и совет обратиться к согласующему; новая карточка допустима после проверки и исправления

#### Scenario: Сервис или LLM недоступны
- **WHEN** отправка завершается таймаутом либо LLM не работает
- **THEN** для таймаута действуют блокировка и сверка confirmed-actions, а без LLM доступ можно оформить кнопочной формой с теми же проверками

### Requirement: Отмена заявки
Стажёр SHALL отменять собственную заявку только в created или in_review через отдельную подтверждённую карточку. После подтверждённой отмены P6 возвращается в «не начат»; approved, rejected, cancelled и спорный исход отменять нельзя.

#### Scenario: Успешная отмена
- **WHEN** владелец подтверждает отмену created и сервис возвращает cancelled
- **THEN** отмена сохраняется, шаг возвращается в исходное состояние и повторная отмена не создаёт нового эффекта

### Requirement: Контракт операций сервиса доступа
Имитация SHALL предоставлять JSON API операций, описанный ниже, с проверкой сервисного вызывающего и пользовательских прав. Успешный ответ SHALL содержать запись объекта; неуспешный — типизированную ошибку. Операции с эффектом SHALL поддерживать ключ и сверку confirmed-actions.

#### Scenario: Валидное создание через API
- **WHEN** доверенный клиент передаёт валидную схему создания для разрешённого стажёра
- **THEN** сервис возвращает объект с уникальным id, status=created, version=1 и сохраняет его до возврата ответа

#### Scenario: Повтор ключа с другими параметрами
- **WHEN** передан существующий operation_key с отличающимся телом
- **THEN** сервис возвращает IDEMPOTENCY_CONFLICT без изменения объекта

Контракт имитации (демонстрационный, не API Авито):

| Операция | Запрос | Успех |
|---|---|---|
| `GET /v1/resources` | идентичность доверенного клиента и пользователя | `{items: Resource[]}` только видимые ресурсы |
| `GET /v1/grants?resource_id=…` | ресурс | `{items: Grant[]}` собственные доступы |
| `GET /v1/access-requests?resource_id=…` | необязательный ресурс | `{items: AccessRequest[]}` собственные заявки |
| `POST /v1/access-requests` | `{operation_key, resource_id, level, justification}` | HTTP 201, `AccessRequest` |
| `GET /v1/access-requests/{id}` | идентификатор | HTTP 200, `AccessRequest` |
| `POST /v1/access-requests/{id}/cancel` | `{operation_key, expected_version}` | HTTP 200, `AccessRequest` с cancelled |
| `POST /v1/operations/{key}/reconcile` | `{}` | общая схема сверки confirmed-actions; разрешена только владельцу попытки |

Все перечисленные поля запроса обязательны, кроме явно необязательного фильтра. Строки непустые; operation_key — UUID; expected_version — целое >= 1; дополнительные поля отклоняются. Владелец определяется из доверенной идентичности, не из тела.

`Resource`: `id:string`, `name:string`, `aliases:string[]`, `can_request:boolean`, `levels:string[]`, `default_level:string|null`, `recommended_team_ids:string[]`, `requires_task:boolean`, `approver_id:string|null`. Скрытые ресурсы не возвращаются.

`AccessRequest`: `id:string` формата `ACC-<число>`, `user_id:string`, `resource_id:string`, `level:string`, `justification:string`, `approver_id:string`, `status:enum(created,in_review,approved,rejected,cancelled)`, `reason:string|null`, `version:integer>=1`, `created_at:datetime`, `updated_at:datetime`. `Grant`: `resource_id`, `level`, `granted_at`, `source_request_id` (строки, время — datetime).

Ошибка: `{error:{code:string,fields:object,retryable:boolean}, existing_id?:string}`. HTTP: 400 `VALIDATION_ERROR`; 401 `UNAUTHENTICATED`; 403 `NOT_ALLOWED` только для видимого объекта; 404 `NOT_FOUND` для скрытого, чужого или отсутствующего; 409 `DUPLICATE_OPEN_REQUEST`, `ALREADY_GRANTED`, `LEVEL_NOT_ALLOWED`, `INVALID_STATE`, `VERSION_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `OPERATION_CLOSED`; 503 `SERVICE_UNAVAILABLE` с гарантией отсутствия обработки. Неизвестный 5xx такой гарантии не даёт. `existing_id` возвращается только для собственной видимой операции.

Переходы: `created -> in_review|approved|rejected|cancelled`; `in_review -> approved|rejected|cancelled`. Терминальные статусы неизменяемы; approved атомарно создаёт Grant. «Результат уточняется» и «Нужна ручная проверка» — состояния попытки AI-buddy, не статусы заявки в сервисе.
