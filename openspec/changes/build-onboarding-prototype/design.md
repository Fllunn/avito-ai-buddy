# Design

## Context

В репозитории пока нет прикладного кода, API и миграций; текущие спецификации пусты. Продуктовое основание — [proposal.md](proposal.md) и подтверждённые `docs/scenarios/00-common.md`–`03-time-off.md`. Семь файлов в `specs/` этого change задают приёмку. Проектные ограничения: Go, React/TypeScript, PostgreSQL, Redis, Docker, только синтетика, проверки прав на бэкенде, реальные LLM не вызываются в тестах.

Технический дизайн вместе со спецификациями и планом задач утверждён пользователем в чате 13.11.2026 («окей, да я утверждаю опенспеку»). Выбор внешнего LLM-сервиса и модели остаётся отдельным решением. При реализации значимые решения оформляются ADR по шаблону `docs/adr/0000-template.md` до соответствующего кода.

## Goals / Non-Goals

**Goals:** обеспечить одно устойчивое состояние чата и плана, заменить имитации реальными клиентами без изменения доменных правил, воспроизводить конкуренцию и сбои, сохранить кнопочные маршруты при недоступности LLM.

**Non-Goals:** распределённые транзакции между помощником и сервисами, Kafka, собственная система корпоративного IAM, настоящий MCP-сервер, векторная БД и отдельный поисковый сервис. Инструменты имеют MCP-подобные схемы и диспетчеризацию внутри Go; сетевой транспорт MCP можно добавить отдельно.

## Decisions

### 1. Компоненты и границы

Один Go API с доменными пакетами `agent`, `authz`, `onboarding`, `tools`; адаптеры `llm`, `storage`, `integrations` подключаются через интерфейсы. Отдельный Go-процесс имитаций предоставляет два независимых HTTP API и локальную панель ведущего. Frontend — React/TypeScript с Vite, TanStack Query/Router, Zustand, Zod по локальным инструкциям.

```text
Browser --> Go API --> domain / tools --> mock HTTP services
               |              |
               v              v
           PostgreSQL      LLM adapter
               |
               v
        durable job worker
Go API --> Redis (cache only)
```

PostgreSQL — источник истины помощника. Имитации используют отдельную БД/схему и отдельного пользователя PostgreSQL: помощник не меняет их таблицы напрямую. Одна PostgreSQL-инсталляция в Compose достаточна, но граница владения данными сохраняется. Redis кэширует только разрешённые справочники с ключом пользователя и версии прав; недоступность Redis ведёт к чтению исходного источника. Сессии, попытки и блокировки конфликтов в Redis не хранятся.

Альтернативы: микросервисы помощника увеличивают стоимость запуска; общие таблицы с имитацией скрывают проблемы интеграций; Redis как очередь требует отдельной гарантии доставки. Для прототипа выбран модульный API и очередь задач в PostgreSQL. До реализации оформить ADR «Модульный API и изолированные HTTP-имитации» и «Устойчивые попытки и очередь PostgreSQL».

### 2. Состояние и время

Основные сущности:

| Сущность | Смысл и важные ограничения |
|---|---|
| `users`, `sessions` | синтетический профиль, роль, команда, дата старта; непрозрачная сессия с серверной проверкой |
| `plan_steps`, `step_assignments` | экземпляры P1–P9 и профильных шагов; владелец, видимость, тип закрытия, зависимости, версия |
| `documents`, `resources` | разрешения, актуальность, ссылки и синтетические материалы; каталог сервиса остаётся авторитетным для заявки |
| `conversations`, `messages` | одна conversation на пользователя; уникальность `(user_id,client_message_id)`, последовательный номер и очищенный текст |
| `cards`, `card_versions` | тип, владелец, параметры, текущая версия, состояние, срок; уникальный активный черновик на `(user_id,type)` |
| `attempts` | карточка и версия, номер попытки, UUID operation_key, снимок параметров, состояние, конфликтный ресурс/даты, срок сверки |
| `service_objects` | локальная проекция подтверждённого результата с номером сервиса, версией и временем последней проверки |
| `jobs` | устойчивые задания обработки, отправки и сверки, lease и следующий запуск |
| `events` | уникальный event_id, причинная попытка/объект, код события и разрешённые поля аналитики |

Обновление результата, проекции плана, сообщения и события выполняется одной локальной транзакцией. Уникальность уведомления: `(service,object_id,service_version,notification_kind)`. Для нескольких ответов одного диалога обработка сериализуется по conversation; операции пользователя в других разделах остаются доступны.

Версия сервисного объекта сравнивается в той же транзакции: более новая обновляет проекцию, равная с тем же содержимым ничего не меняет, меньшая не откатывает данные. Равная версия с другим содержимым — ошибка контракта с сохранением последнего подтверждённого снимка. Сверка ключа возвращает исходный результат операции, а не обязательно последний статус объекта: попытку можно завершить по этому результату, сохранив более новую локальную проекцию. Если её ещё нет, результат сохраняется с исходным временем и запускается чтение актуального объекта; позднее уведомление не объявляет устаревший статус текущим.

Время — интерфейс Clock. Для воспроизводимых примеров `DEMO_NOW=2026-11-12T12:00:00+05:00`, `DEMO_TIMEZONE=Asia/Yekaterinburg`; в обычном режиме текущее серверное время, отображаемое в настроенном поясе. Храним мгновения в UTC, даты отгула как даты без времени. Часы и календарь одинаково конфигурируются у API и имитаций. В тестах время заморожено и переводится явно, включая истечение черновика и начало отгула.

Уточнение утверждено пользователем 13.11.2026 («Да, разделить часы»): бизнес-Clock и операционный Clock независимы. DEMO_NOW задаёт бизнес-время для дат, правил, сроков карточек/подтверждений и пользовательских отметок. Расписание jobs, lease, интервалы сверки и технические длительности используют реальные UTC-часы, даже когда бизнес-время заморожено. Операционные мгновения сохраняются в PostgreSQL и не пересчитываются при перезапуске; в тестах оба Clock подменяются независимо. У попытки отдельно сохраняется операционный момент подтверждения для измерения длительности. API и имитации используют общий бизнес-Clock; фиксация даты демо не останавливает очередь. Решение — ADR 0009.


Неделя = `floor((local_today-start_date)/7)+1`. До старта запись плана и сервисные действия отключены. Срок карточки — 24 часа от последней правки; новая версия обновляет срок, отмена черновика возвращает только временную отметку «в работе», но не откатывает подтверждённые результаты.

### 3. Демо-вход и разрешения

Выбор пользователя выполняется только через демо-вход из фиксированного списка. Сервер создаёт непрозрачную cookie-сессию с HttpOnly/SameSite, проверяет Origin на изменяющих запросах; браузер не задаёт роль. Переключение пользователя завершает текущую сессию и очищает клиентский кэш. Разрешённый источник frontend задаётся конфигурацией, а не wildcard.

Клиент помечает запросы поколением текущей сессии: при переключении отменяет доступные запросы и опрос, удаляет личные данные Query/Zustand и не принимает поздние ответы прежнего поколения. Задания хранят исходного владельца независимо от браузерной сессии: выход не отменяет уже подтверждённое действие и не переносит его новому пользователю. Перед отправкой worker проверяет актуальные полномочия исходного владельца, а не наличие открытой вкладки.

Сервисные клиенты передают секрет доверенного backend и actor_id по внутренней сети; имитация получает роль и команду actor из собственного сида и повторяет проверки. Неавторизованный клиент не может навязать actor. Браузер общается только с API помощника. Отдельные полномочия ведущего открывают управление имитациями; они не принимаются за пользовательскую сессию. Демо-вход и панель маркируются и включаются только в демо-конфигурации.

Матрица прав из `identity-and-permissions` применяется до выдачи DTO и до контекста LLM. Внешняя роль не даёт доступ к личному плану стажёра. Назначения наставника/руководителя показываются в их собственном списке и отражаются разрешённой проекцией в плане стажёра. Прямые обращения к чужому id не раскрывают существование объекта. Кэш включает версию политики; перед подтверждением читаются актуальные права из авторитетного источника.

### 4. Очистка сообщений

До БД и внешнего LLM работает локальный интерфейс очистки. В демо он маскирует проверяемые категории из тестового корпуса: медицинские причины, семейные сведения, номера документов/карт, пользовательские секреты. При подозрении на чувствительное содержимое без надёжно выделенных границ сохраняется только `[чувствительное сообщение скрыто]`, модель не вызывается и предлагается структурированная форма. Если очистка завершилась ошибкой, применяется тот же закрытый режим. Сырой текст не попадает в логи и фоновые задания.

Карточки и сервисные DTO строятся по разрешённому набору полей. Для отгула это даты; причина отсутствия не является полем. Обоснование доступа и причина отказа ведущего тоже проходят очистку. Тело ответов провайдера не включается в ошибки логирования. Исходный сырой ввод не сохраняется для «будущего анализа».

Альтернатива — отправлять сырой текст модели для очистки — нарушает выбранную границу передачи данных. Локальная очистка не гарантирует распознавание любых ПДн в произвольном естественном языке: прототип проверяется на синтетическом корпусе, для внедрения потребуется отдельная оценка качества. До реализации оформить ADR об обработке чувствительного ввода.

### 5. HTTP API и обновление интерфейса

API отвечает быстро, длительная работа возвращает `202` с идентификатором задания. Frontend опрашивает состояние активной работы с интервалом 1 с, прекращает опрос после завершения и возобновляет при открытии страницы. На открытии плана и явной проверке запускается отдельное обновление бизнес-статусов. Постоянного фонового опроса всех согласований и push-уведомлений вне открытого интерфейса нет.

Интервал 1 с относится к активным заданиям и сверке, а не к непрерывной проверке согласований. Если ведущий одобрил заявку после завершения задания, обновление обнаруживается при повторном открытии плана или кнопкой проверки; это явно включается в демо-инструкцию. Уведомление «агент пишет первым» означает сообщение после получения изменения от сервиса, без отдельной реплики пользователя в чате.

| Endpoint | Вход | Выход |
|---|---|---|
| `POST /api/demo/session` | `{user_id}` из сида | cookie и `{profile}` |
| `DELETE /api/session` | — | 204 |
| `GET /api/me` | — | `{profile,capabilities}` |
| `GET /api/onboarding` | — | `{steps,next_steps,waiting_on_others,requests,as_of,refresh_job_id?}` |
| `GET /api/chat?after=…` | необязательный курсор | `{items,next_cursor,active_cards}` |
| `POST /api/chat/messages` | `{client_message_id,text}` | 202 `{message_id,job_id}` после очистки и записи |
| `POST /api/dialogue/actions` | `{client_message_id,intent,slots}` по схеме намерения | `{job_id?,message_ids,card?}`; кнопочный путь без LLM |
| `POST /api/cards` | `{type,parameters}` по схеме типа | `{card}` после проверок |
| `PATCH /api/cards/{id}` | `{expected_version,changes}` | `{card}` новой версии |
| `POST /api/cards/{id}/confirm` | `{expected_version}` | 202 `{attempt_id,job_id,state}` либо существующая попытка |
| `POST /api/cards/{id}/discard` | `{expected_version}` | `{card}` с отменённым черновиком |
| `GET /api/attempts/{id}` | — | `{state,result?,as_of,next_check_at?}` |
| `POST /api/attempts/{id}/reconcile` | — | 202 `{job_id}`; параллельные клики объединяются |
| `POST /api/attempts/{id}/retry` | — | повтор с прежним ключом после явной недоступности либо новая попытка после not_created и повторных проверок |
| `POST /api/requests/refresh` | `{kind,id?}` | 202 `{job_id}` для своих объектов |
| `GET /api/jobs/{id}` | — | `{state:queued|running|completed|failed,result?,error?}` |
| `POST /api/steps/{id}/confirmation` | `{expected_version,target_state}` | `{confirmation_id,summary,expires_at}` |
| `POST /api/steps/{id}/confirm` | `{confirmation_id}` | `{step}` после перепроверки владельца, версии и зависимости |

Общие DTO: идентификаторы — непустые строки, версии — целые >= 1, даты — ISO date, мгновения — RFC3339; неизвестные поля отклоняются. Тело изменяющего запроса содержит только перечисленные поля. Ошибки API: `{error:{code,fields,retryable},request_id}`; 400 — схема/параметры, 401 — сессия, 403 — видимый запрет, 404 — неизвестное/чужое, 409 — версия/конфликт/состояние, 503 — инфраструктура. Текст UI строится по коду, закрытые сведения не копируются из сервисной ошибки.

Для `parameters` и `slots`: доступ — `{resource_id,level,justification}`, отгул — `{start_date,end_date}`, отмена — `{kind,id}`; недостающие параметры разрешены в уточнении, но не в готовой карточке. Схемы совпадают в карточках, доменной валидации и инструментах. Подтверждение шага действительно 5 минут и однократно по версии; повтор возвращает прежний результат. Эта короткая форма подтверждения не является сервисной карточкой.

Для текстового и кнопочного ввода client_message_id имеет общую область уникальности на пользователя. Сохраняется вид запроса и каноническое очищенное содержимое: одинаковый повтор возвращает прежнюю обработку, другой текст/intent/slots под тем же id даёт 409 `MESSAGE_ID_CONFLICT`. Сырой текст и его отпечаток не сохраняются.

TanStack Query хранит серверные данные; Zustand — только временное UI-состояние, не авторитетный статус заявки. Все ответы проверяются Zod. Результаты действий перезапрашивают историю и план. Для отказа основного PostgreSQL клиент сохраняет на экране известный снимок и показывает недоступность сохранения, не объявляя неподтверждённый успех.

Альтернативы: SSE/WebSocket дают меньше задержку, но требуют дополнительного восстановления соединения; простой опрос достаточен для демо. Решение фиксируется ADR перед реализацией.

### 6. Подтверждение, конкурентность и восстановление

Состояния карточки: `draft`, `confirmed`, `discarded`, `expired`, `replaced`. Типы: `access_create`, `time_off_create`, `access_cancel`, `time_off_cancel`. Состояния попытки: `queued`, `sending`, `succeeded`, `rejected`, `unavailable`, `unknown`, `manual_review`, `not_created`.

Подтверждение выполняет проверки и берёт короткую блокировку строки пользователя в PostgreSQL, перечитывает актуальную карточку, проверяет конфликтующие попытки и создаёт попытку и задание одной транзакцией. Уникальность `(card_id,version,attempt_no)` и operation_key защищает сетевые повторы. Ожидание HTTP не удерживает блокировку БД. В сервисе независимо проверяются открытые заявки и пересекающиеся даты, чтобы закрыть гонку с изменениями вне помощника.

Worker забирает задания с lease, отправляет неизменяемый снимок параметров с operation_key. Перед фактической отправкой повторно проверяет текущие права и применимые ограничения. Перезапуск при истёкшем lease после возможной отправки ведёт к сверке, а не к слепой новой операции. Сверка и ответ на поздний вызов используют один журнал ключей в имитации.

Отказ проверки до первой отправки сохраняется как rejected с источником `local_validation`, без выдуманного ответа сервиса. Если отправка уже могла состояться, сначала выполняется сверка: отзыв права на новое действие не доказывает отсутствия старого результата; раскрытие найденных данных всё равно проверяет текущие права. В отсутствие руководителя отгул блокируется до карточки; ошибки чтения каталога/профиля не заменяются выбором согласующего пользователем.

В сервисе транзакция ключа и бизнес-объекта атомарна. Повтор того же ключа с тем же телом возвращает исходный ответ, с другим — IDEMPOTENCY_CONFLICT. Сверка `pending` не разрешает повтор. Если операции действительно нет, сервис атомарно записывает закрывающую запись `not_created`; поздняя отправка под этим ключом получает OPERATION_CLOSED. Это устраняет гонку «сверка не нашла, старый запрос создал позже». Для completed ответ включает исходный результат успеха или отказа по контракту `confirmed-actions`.

Неизвестный исход сохраняет конфликтную резервацию: доступ — `(user_id,resource_id)`, отгул — пересекающиеся рабочие дни пользователя. После manual_review резервация не снимается автоматически. Кнопка проверки запускает не более одного задания сверки. После окончательного not_created новый ключ создаётся только по явному запросу пользователя и новым проверкам; устаревшая карточка требует новой версии и подтверждения. После unavailable повтор использует тот же ключ. Изменение параметров всегда требует новой карточки/версии, а не подмены снимка попытки.

«Отправить заново» показывает итоговые параметры и служит явным подтверждением только неизменной версии в пределах её TTL; одинаковые конкурентные retry объединяются в одну новую попытку. Истечение срока или изменение параметров сначала создаёт новую версию карточки, которую нужно подтвердить отдельно. Автоматическая сверка сама не создаёт новую попытку с новым ключом.

Успех в сервисе, но ошибка локальной БД: устойчивое задание и попытка уже существуют. После восстановления БД worker получает результат по ключу и одной транзакцией сохраняет проекцию объекта, шаг, сообщение и события. Временный отказ БД не требует повторного подтверждения внешнего действия. Неподтверждённый результат не отображается как окончательный успех.

### 7. Инструменты и LLM

Инструмент имеет имя, описание, JSON Schema входа/выхода, признак изменения состояния и обработчик с проверкой прав. Вход не включает user_id или роль; они берутся из системного контекста. Диспетчер не выполняет произвольный URL или неизвестное имя из вывода модели.

| Инструмент | Вход | Выход |
|---|---|---|
| `onboarding.get_plan` | `{}` | разрешённый план и состояния |
| `documents.search` | `{query:string}` | `{items:[{id,title,url,fragment_ids,fragments,stale,demo}]}` после фильтра прав |
| `access.list_resources` | `{query?:string}` | видимый каталог |
| `access.get_status` | `{request_id:string}` | собственный AccessRequest |
| `access.create_request` | `{resource_id,level,justification}` | AccessRequest либо типизированная ошибка |
| `access.cancel_request` | `{request_id,expected_version}` | AccessRequest либо ошибка |
| `time_off.get_status` | `{request_id:string}` | собственный TimeOffRequest |
| `time_off.create_request` | `{start_date,end_date}` | TimeOffRequest либо ошибка |
| `time_off.cancel_request` | `{request_id,expected_version}` | TimeOffRequest либо ошибка |

Мутации требуют серверного контекста подтверждённой попытки: `card_id`, версия, attempt_id и operation_key; LLM не может его создать. DTO инструментов закрыты для дополнительных полей и наследуют ограничения сервисных контрактов. Чтение не требует карточки, но требует проверки прав. Модель предлагает намерения и параметры; backend сам выбирает допустимый маршрут, проверяет данные и инициирует инструменты после подтверждения.

Интерфейс провайдера разделяет распознавание намерений и подготовку ответа. Структурированный результат распознавания: `{intents:[{name,slots,confidence}],ambiguities:[]}` с разрешённым enum намерений M-2, не команда на выполнение. confidence < 0.8 либо неоднозначность означает уточнение; это демо-порог, не оценка вероятности корректности модели. Некорректный JSON, неизвестный класс и неверные поля приводят к безопасному кнопочному пути. Контекст содержит только профиль текущего пользователя, разрешённые данные и очищенную историю; команды внутри документов не имеют полномочий.

Первая реализация включает fake для детерминированных маршрутов. Внешний адаптер реализуется после выбора сервиса, его протокол проверяется по официальной документации и оформляется ADR; уже выбранные доменные интерфейсы и правила приёмки от этого не зависят. До подключения внешнего провайдера нельзя считать свободный диалог с настоящей LLM готовым. Fake явно обозначен и не выдаётся за реальную модель.

Для малого корпуса документов используется поиск по названиям, синонимам и фрагментам с фильтром прав; векторный поиск не нужен. Чтобы требование «нет неподтверждённых утверждений» было проверяемым без второй LLM-судьи, модель выбирает fragment_id и границы цитируемого фрагмента; backend проверяет принадлежность и формирует фактический ответ из этих фрагментов с доверенным шаблоном и ссылками. Свободный неподтверждаемый пересказ не показывается. Максимум одна повторная генерация в пределах общего таймаута, затем ссылки. Отбор следующего шага, статусы, контакты и тексты сервисного результата формируются кодом.

Альтернатива — проверять произвольный пересказ ещё одной моделью — добавляет стоимость и не гарантирует достоверность; свободный пересказ можно расширить отдельным изменением после оценки. Для выбранного провайдера и режима ответов оформить ADR до реализации адаптера.

### 8. Имитации и панель

Нормативные схемы обоих API — в `specs/access-requests/spec.md`, `specs/time-off-requests/spec.md` и `specs/confirmed-actions/spec.md`. Строки времён — RFC3339, даты — ISO. Общий журнал операций хранит actor, key, хэш тела и исход. Доступы, отсутствие и операции сверки используют одинаковый контракт надёжности, но отдельные бизнес-правила.

Панель ведущего предоставляет:

| Управление | Тело | Эффект |
|---|---|---|
| `PATCH /demo/access-requests/{id}/status` | `{expected_version,status,reason?}` | допустимый переход; rejected требует непустую очищенную причину до 500 символов |
| `PATCH /demo/time-off-requests/{id}/status` | та же схема | допустимый переход с проверкой времени |
| `PUT /demo/faults/{service}` | `{mode,delay_ms}` | режим normal / unavailable_before / delay_before / lose_response_after / reconciliation_unavailable |
| Раздел сброса в панели | инструкция `make demo-reset CONFIRM=demo` | предупреждение о полном удалении демо-данных и команда согласованного сброса всего стенда |

Панель реализуется простыми страницами на Go templates; новый frontend-фреймворк для неё не вводится. Мутации требуют отдельной сессии ведущего и проверки Origin. Управляющие endpoints недоступны пользовательскому браузерному API; порты панели привязываются к localhost. Режим lose_response_after сначала фиксирует объект, затем обрывает ответ, что принципиально отличается от unavailable_before. Для сбоя локального сохранения применяется тестовый адаптер хранилища в интеграционных тестах, а не открытый пользовательский endpoint.

Полный сброс выполняет локальная команда оркестрации: проверяет демо-конфигурацию и явное подтверждение, останавливает API/worker и имитации, удаляет только выделенные демо-данные их БД и кэш, затем применяет миграции/сиды и запускает компоненты после проверок готовности. Сессии, история, карточки, попытки, jobs, события, объекты и журналы ключей сбрасываются вместе; очистка только имитаций при работающем worker запрещена. При ошибке стенд остаётся остановленным до повторного успешного сброса. Чужие Compose-проекты и тома команда не затрагивает. Панель не оркестрирует контейнеры и не получает доступ к Docker socket.

### 9. Параметры демо

| Параметр | Предложенное значение |
|---|---|
| `CARD_TTL` | 24h |
| `LLM_TIMEOUT` | 20s на обработку, включая допустимую повторную генерацию |
| `SERVICE_TIMEOUT` | 3s на вызов |
| `RECONCILE_DELAYS` | 1s, 3s, 10s, 30s, 60s последовательно после неизвестного исхода |
| `CLIENT_POLL_INTERVAL` | 1s при активной работе |
| `STEP_CONFIRMATION_TTL` | 5m |
| `SESSION_TTL` | 8h |

Все значения валидируются при запуске; некорректная конфигурация даёт понятную ошибку без запуска неполного сервиса. После пяти безрезультатных сверок — manual_review, дальнейшая проверка только по явному запросу/открытию объекта, без обещания бесконечного фонового опроса. Новая ручная проверка не обнуляет лимит и не снимает блокировку. Перезапуск сохраняет число проверок и время следующей.

### 10. Аналитика, тестирование и покрытие

События пишутся в PostgreSQL в локальной транзакции результата; ключи дедупликации соответствуют попытке и версии перехода. Семейства событий и поля — `docs/metrics.md`, кроме feedback, остающегося в backlog. Q-1 считается по актуальному исходу уникальной попытки, а не сумме промежуточных событий. U-2 — технический прокси «нет эскалации и есть ответ с источником/результат», а не доказательство решения вопроса; эффект на нагрузку проверяется пилотом по docs/metrics.md.

Тесты: Go table-driven доменные проверки, HTTP-контрактные тесты имитаций и адаптеров, интеграционные PostgreSQL-тесты транзакций и конкуренции, Vitest/RTL/MSW для UI и сценарная проверка собранного приложения. Для обязательных сценариев создаётся явная карта «требование -> тест»; настоящая LLM в автотестах не вызывается.

Одна команда `make coverage` поднимает тестовые зависимости, выполняет проверки и выдаёт backend/frontend/mocks плюс общий отчёт. Процент общий = сумма покрытых строк / сумма учитываемых строк, не среднее процентов. Каждый из трёх модулей также проверяется на > 80%, чтобы высокий backend-процент не скрывал непроверенный UI. Служебные entrypoints могут исключаться только если в них нет прикладной логики; общее требование кейса имеет приоритет над формальным исключением каталога cmd. Правила подсчёта и версии инструментов описываются в README.

Знаменатель включает все прикладные исходники, в том числе не импортированные тестами. Для Go исходный профиль блоков преобразуется в отчёт исполняемых строк: строка с исполняемыми операторами учитывается один раз и считается покрытой, только если все относящиеся к ней исполняемые блоки имеют ненулевой счётчик. Комментарии, пустые строки и строки только с разделителями не учитываются. Для TypeScript используется line coverage с включением всех прикладных файлов. Нативный процент операторов Go сохраняется отдельной диагностикой и не подменяет требование по строкам. Алгоритм проверяется фикстурами с несколькими операторами на строке, частично покрытыми ветвями, неимпортированным файлом и точной границей 80%.

Комплект сдачи проверяется отдельно от автотестов: продуктовая PDF-презентация, README, репозиторий/ZIP, отчёт покрытия и SDD; запись демо показывает запрос, подтверждение и сохранённый результат. Отсутствие видео отмечается явно и не приравнивается к отсутствию работающего прототипа. Доступ жюри к приватному репозиторию и загрузку на платформу обеспечивает человек. В презентации фиксируются фактически проверенный режим LLM, ограничения и план пилота без выдуманных результатов экономии.

## Risks / Trade-offs

- [Объём трёх сценариев] → реализация этапами: сначала сквозной доступ, затем документы и свободный диалог, затем отгул; общий change считается выполненным только после всей приёмки.
- [Произвольный чувствительный ввод] → локальная очистка, закрытый режим при сомнении, структурированные формы, синтетический тестовый корпус; перед реальным внедрением отдельная оценка.
- [Сверка реального сервиса может не поддерживать ключ] → выбранный протокол — контракт имитаций; реальный адаптер обязан явно определить эквивалент восстановления, иначе неизвестный исход требует ручной проверки без повтора.
- [Опрос даёт задержку до интервала клиента] → 1 с при активной работе, статус ожидания сразу; пользовательские локальные действия проверяются отдельно от внешней задержки.
- [Демо-статусы синтетические] → панель и инструкция явно маркируют имитации, это не реальное согласование.
- [Внешняя модель не выбрана] → архитектура и кнопочный путь реализуются независимо; выбор и проверка реального адаптера обязательны до заявления о готовом AI-диалоге.

## Migration Plan

Существующих пользовательских данных нет. При реализации добавить версионированные миграции и повторяемый сид, затем Compose health checks и порядок старта. Сброс демонстрации удаляет только явно выбранные демо-данные и требует подтверждения в панели/документированной команде. Перезапуск без сброса сохраняет историю и операции. Откат приложения выполняется совместимой версией с сохранёнными томами; перед изменением схемы — резервная копия демо-БД, несовместимые миграции не откатываются автоматически.

## Open Questions

Конкретный внешний LLM-сервис и модель пока не выбраны по исходным правилам проекта. Это не блокирует реализацию провайдерной абстракции, кнопочных маршрутов и тестов с fake; блокирует только подключение реальной модели. Перед соответствующей задачей выбрать сервис, проверить протокол и оформить ADR. Прочие влияющие на поведение решения утверждены вместе с требованиями 13.11.2026.
