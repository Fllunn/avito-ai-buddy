# Design

## Context

Основание — [proposal.md](proposal.md). `Makefile` уже содержит race-тесты, интеграционный стенд и `make coverage`. `scripts/coverage/run.sh` запускает оба Go-модуля и frontend, проверяя строго >80% строк. Без TEST_API_DATABASE_URL/TEST_REDIS_ADDR некоторые тесты пропускаются. Отдельного CI и конфигурации golangci-lint сейчас нет. В `backend/go.mod` указан Go 1.27.0; поддержка этой версии анализаторами подлежит явной проверке.

Уже существуют тесты на отзыв прав, конкурентное подтверждение, неизменяемый снимок, атомарность, потерю lease, неизвестный исход, сохранение графика сверки и фильтрацию ответа LLM. Они используются как база матрицы, а не дублируются. Правила `backend/AGENTS.md` и `mocks/AGENTS.md` сохраняются.

## Goals / Non-Goals

**Goals:** одна точка запуска, доказательство полноты исполнения, тестирование свойств и неблагоприятных последовательностей событий, компактные результаты для агента, объяснимые настройки.

**Non-Goals:** изменение продуктового поведения, автоматическое исправление исходников, замена человеческого security review, доказательство отсутствия всех уязвимостей. IDE не является обязательной зависимостью. Никакой отправки кода в SaaS и настоящих вызовов LLM.

## Decisions

### 1. Профили и оркестрация

- `make review-fast`: preflight, форматирование в режиме проверки, build/vet и golangci-lint двух Go-модулей, детерминированные unit-тесты, сканирование текущих исходников на секреты. Не заявляет полноту интеграционных проверок; каждый skip виден в отчёте.
- `make review-deep`: всё выше, govulncheck, изолированный PostgreSQL/Redis, интеграционные тесты с `-race -shuffle` и явным seed, выбранные конкурентные тесты с `-count=20`, фаззинг, существующий `make coverage`, сканирование git-истории на секреты. Повтор race-прогона покрытия допускается ради сохранения единого существующего контракта; дополнительные дубли обычных тестов исключаются.
- Таймаут отдельного обычного тестового процесса 10 минут; лимит workflow быстрого профиля 15 минут, глубокого 45 минут. Это первоначальные ограничения ресурсов, не обещание времени выполнения. Fuzz — 60 секунд на каждую из не более шести выбранных целей, общий лимит 10 минут с запасом на сборку; число fuzz workers по умолчанию 2. Переопределения сохраняются в отчёте.
- Отказ одного этапа не отменяет независимые этапы. Зависимые этапы получают `blocked`, никогда `passed`. Ошибки инфраструктуры завершают общий процесс ненулевым кодом. Перехватываются INT/TERM и ошибки запуска процесса. Окончательные сведения сохраняются атомарно в каталоге отдельного run.

Альтернатива — запуск несвязанных команд вручную; отклонена из-за скрытых пропусков и потери итогового статуса. Оркестрация — shell плюс небольшой Go CLI в `scripts/review/` при необходимости структурного разбора; новый язык и runtime не добавляются. Для CLI обязательны тесты обработки процессов и отчётов.

### 2. Набор инструментов и воспроизводимость

| Средство | Решение | Основание |
|---|---|---|
| gofmt/goimports | Проверка без записи | Существующие правила проекта |
| golangci-lint v2 | Явный список вместо enable-all | Предсказуемость при обновлении, минимум шума |
| Базовые анализаторы | govet, staticcheck, errcheck, unused, ineffassign | Ошибки и подозрительные конструкции |
| Контекст и ресурсы | contextcheck, noctx, bodyclose, sqlclosecheck, rowserrcheck | Отмена и закрытие HTTP/pgx ресурсов; реальную поддержку pgx проверяют контрольные примеры |
| Ошибки и исключения | errorlint, nilerr, nolintlint | Корректная обработка ошибок, объяснимость подавлений |
| Дополнительная безопасность | gosec | Сигнатурные проверки в дополнение к ручному анализу; ложные срабатывания рассматриваются поштучно |
| govulncheck | Весь модуль и стандартная библиотека согласно возможностям версии | Известные уязвимости и достижимость |
| Gitleaks | Текущие файлы и отдельно история, полностью редактированные значения | Секреты не покрываются обычными тестами |
| Go fuzz/race | Встроенные инструменты | Без нового тестового фреймворка |

Версии бинарников, checksum и Go toolchain фиксируются в `scripts/review/tools.lock.json` после проверки совместимости и контрольного запуска. Здесь не назначается непроверенный номер версии. Установка только в локальный служебный каталог, без `@latest`, `curl | sh` и изменения глобальных конфигураций. Несовместимый инструмент — явная блокировка этапа; не заменять её отключением анализатора. Полная настройка не считается принятой, пока весь обязательный набор не работает.

Не использовать массовые исключения каталогов/tests или baseline, скрывающий текущие дефекты. Конкретное исключение документируется правилом, расположением и причиной. Стилевые лимиты длины функций и строк не добавляются без выявленной пользы. При обнаружении продуктовых дефектов отчёт честно остаётся красным; изменение не превращается в несогласованный рефакторинг.

### 3. Матрица инвариантов и усиление тестов

`scripts/review/invariants.json` связывает ID, spec/ADR, тесты, вид проверки и oracle. Тестовый JSON-поток Go используется для проверки, что обязательные тесты реально исполнились; одного совпадения имени с исходником недостаточно. Изменение/удаление обязательного теста без обновления матрицы вызывает ошибку. Проверяем полноту самой матрицы её тестовыми фикстурами.

| Область | Обязательные свойства / углы | Где расширять |
|---|---|---|
| Права | Четыре роли, disabled, другая команда/владелец, отзыв во время LLM и очереди; отсутствие запрещённых данных в контексте/истории/журнале | authz, api, agent, storage |
| Подтверждение | До/на/после TTL по спеке, устаревшая версия, изменённые параметры, дубль, отсутствие Authority | tools, actions, storage |
| Очередь | Конкурентный claim, потеря lease, старый worker, restart, потеря ответа, прежний operation_key, manual_review | actions, storage, integrations, mocks |
| Сохранение | Ошибка перед commit, отсутствие частичного успеха, дедупликация события, монотонная версия | storage |
| Отсутствия | 1/5/6 рабочих дней, 90-дневная граница, выходные/праздники, високосная дата, два порядка переноса и остановка после unknown | calendar, api, mocks |
| LLM и схемы | Неизвестные поля, повреждённый JSON, trailing input, недоверенные ссылки/фрагменты, prompt injection, поздний ответ | agent, tools, safety |
| Деградация | Redis отключён, сервис недоступен до отправки, ответ потерян после эффекта, таймаут и отмена | catalog, integrations, api |

Сначала сопоставить перечисленные существующие тесты с матрицей; добавлять только отсутствующие утверждения и последовательности. Property tests используют стандартные `testing`/`testing/quick` либо явный генератор с seed; oracle задаётся независимо: разрешённые множества, конечный автомат, границы из спецификации. Конкуренция управляется барьерами/каналами и fake Clock, не ненадёжными sleep. Повторяемые интеграционные тесты сами очищают свои данные.

Fuzz targets: календарный разбор/валидация, закрытые схемы agent/tools, обработка текста safety и проверка fragment/URL при наличии подходящей чистой границы. Фикстуры ограничивают размер входа; каждый вызов детерминирован и не ходит в сеть/БД. Seed corpus покрывает известные плохие входы, а найденные минимальные примеры сохраняются только после проверки синтетичности. «Нет паники» дополняется свойством контракта для каждого target.

Для самопроверки качества тестов применяются несколько точечных контролируемых мутаций: разрешить запрещённую роль, принять устаревшую карточку, снять защиту версии результата. Только временная копия выбранных файлов/модуля, никогда рабочие исходники; целевой тест обязан упасть именно на нарушенном утверждении, а не при компиляции. Это фиксированный небольшой набор, не заявление о полном mutation coverage. Бюджет этапа 5 минут; каждый мутант и результат в отчёте.

### 4. Отчёты и экономия контекста

Каталог `output/review/<run-id>/`: `summary.md` (не более 100 строк), `summary.json`, безопасные логи, результаты Go JSON, ссылки на покрытие и fuzz corpus. Сводка содержит профиль, UTC-время, commit при наличии, dirty-флаг и hash входных файлов, версии, seed/бюджеты, этапы и инварианты. Одного HEAD недостаточно для изменённой рабочей копии. Статусы: passed/failed/blocked/skipped; все обязательные этапы должны иметь passed.

Логи и JSON сканера используют redaction до сохранения; отчёты не содержат `.env`, HTTP bodies, ключей или контекста реальной модели. У тестовых примеров только синтетические данные. В CI публикуются лишь разрешённые безопасные файлы, не весь output и не дампы БД. История/неотслеживаемые файлы и регрессионный corpus проверяются на секреты; локальные секретные файлы не печатаются. Правила сканирования и исключения документированы.

### 5. CI и редакторы

Workflow готовится локально: `pull_request` — быстрый профиль и обязательные интеграционные инварианты; `workflow_dispatch` и еженедельный `schedule` — глубокий профиль. Полный глубокий запуск перед приёмкой обязателен независимо от PR. Использовать `contents: read`, actions закрепить SHA, checkout без сохранения credentials, без `pull_request_target`, production secrets и self-hosted runners. Тестовые credentials синтетические. Для сканирования истории fetch-depth обеспечивает нужную полноту. Кэш ключуется версиями и lock-файлами, не даёт права считать старый отчёт актуальным.

Редактор может вызывать те же make-команды. Установка расширений в личный профиль пользователя не входит в проектную настройку; обязательная проверка доступна без редактора. Сами инструменты линтинга и поиска секретов работают локально. govulncheck получает публичную базу уязвимостей; это сетевое требование явно отражается в preflight, исходники внешнему сервису не отправляются.

### 6. Источники и ADR

До реализации оформить ADR по проектному шаблону: требования → средство/значение → альтернативы → последствия → проверка → условие пересмотра. Включить начальные бюджеты и необходимость пересмотра после первого прогона.

- [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) — контекст, ошибки и горутины.
- [Go fuzzing](https://go.dev/doc/security/fuzz/) — встроенный фаззинг, детерминированность и corpus.
- [Race detector](https://go.dev/doc/articles/race_detector) — проверяет только выполненные пути; гонки БД проверяются отдельными инвариантами.
- [govulncheck](https://go.dev/doc/tutorial/govulncheck) — известные уязвимости и вызовы.
- [golangci-lint FAQ](https://golangci-lint.run/docs/welcome/faq/) и [конфигурация](https://golangci-lint.run/docs/configuration/file/) — совместимость toolchain и явные правила.
- [Gitleaks](https://github.com/gitleaks/gitleaks) — поиск секретов; при фиксации версии проверить поддержку и параметры redaction.
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) — выборочные требования безопасности; это не сертификация ASVS.

## Risks / Trade-offs

- Ограниченный fuzz-бюджет не исследует все входы → сохранять corpus, варьировать seed, оставлять ручной анализ.
- Повтор race-тестов не доказывает корректность протокола → независимые assertions по внешним эффектам и БД.
- Coverage >80% не измеряет качество oracle → критические инварианты и контролируемые мутации.
- Инструменты могут найти много старых дефектов → не скрывать baseline; отделять настройку проверок от продуктовых исправлений.
- Повтор тестов может выявить глобальные фикстуры → изоляция данных и явный отчёт о нестабильности, не автоматический retry до зелёного.
- Загрузка базы уязвимостей/образов требует сети → пререквизиты, проверенные версии и честный blocked, а не ложный успех.

## Migration Plan

После человеческого утверждения реализовать инструментальную основу и её тесты, затем матрицу и недостающие сценарии, затем CI и документацию. Выполнить быстрый и полный глубокий прогон, сохранить реальные результаты и ограничения. Существующие команды продолжают работать. Откат — удалить добавленные цели/скрипты/workflow и вернуть конфигурации; миграции данных и production-развёртывание не нужны. Файлы чужого незавершённого deployment не менять.
