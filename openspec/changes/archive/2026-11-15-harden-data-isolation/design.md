# Design

## Context

Основание — [proposal.md](proposal.md) и [отчёт ревью изоляции](../../../../output/isolation-review/report.md). Тесты-доказательства лежат в `output/isolation-review/evidence/` и на текущем коде падают: `TestIsoServiceObjectOwnerNotBound` (IR-01), `TestIsoSideChannelGlobalMessageIDs` (IR-03), `TestIsoOfferNextJoinsForeignCard` (IR-02), Vitest `second tab of the same browser (P3 demo)` (IR-04). Остальные тесты ревью проходят и должны проходить после изменения.

Текущее устройство:

- **Проекция заявок.** `saveObject` ([results.go](../../../../backend/internal/storage/results.go)) читает строку по `(service, object_id)` без владельца и делает upsert `ON CONFLICT(service,object_id) DO UPDATE SET payload=…`, не трогая `user_id`. `cleanResult` уже проверяет `object.UserID == user` для пришедшего объекта, но не для сохранённой строки. Для доступа транзакция случайно откатывается в `projectAccessPlan` (`no rows`), для отгула — фиксируется. Ошибка `Finish` у worker переводит попытку в `Uncertain` → сверка → `manual_review`. Ошибка `ApplyObject` в refresh даёт код `SERVICE_UNAVAILABLE`.
- **Идентификаторы сообщений.** `messages.id` — `GENERATED ALWAYS AS IDENTITY`. Поле `actions.Message.ID` сериализуется как `id`. `POST /api/chat/messages` возвращает `message_id: m.ID`, `POST /api/dialogue/actions` — `message_ids: [m.ID]`. Внутри `messages.id` используется в `jobs.message_id`, `cards.origin_message_id`, `notifications.message_id`, событиях `message:<id>` и `execution_links(kind='message')`. Наружу ссылки маршрутов `kind='message'` не отдаются (`ExecutionRepository.Read` фильтрует `parent`/`operation_parent`/`job`). Личная `sequence` уже есть, уникальна в паре `(user_id, sequence)` и отдаётся в ленте. Фронтенд использует `id` только как React-ключ, а `message_id`/`message_ids` не использует.
- **OfferNext.** Запрос в [runtime.go](../../../../backend/internal/storage/runtime.go) соединяет `dialogue_state` и `cards` по `card_id` без `user_id`, подзапросы `attempts` и чтение статуса первой карточки переноса — тоже без `user_id`.
- **Вкладки.** HttpOnly cookie общий для вкладок. `request()` во фронтенде отсекает поздние ответы только внутри вкладки (поколение `generation`). `me` не перечитывается при фокусе (`refetchOnWindowFocus: false`). CORS разрешает только заголовок `Content-Type`.

## Goals / Non-Goals

**Goals:**

- закрыть IR-01–IR-04;
- превратить тесты-доказательства в регрессионные, остальные тесты ревью изоляции и безопасности сохранить зелёными;
- не менять схему БД и контракт имитаций, сохранить типы полей публичного API.

**Non-Goals:**

- IR-05 — только ADR;
- глобальные номера `ACC-`/`ABS-` в имитациях;
- `BroadcastChannel`, синхронизация вкладок в реальном времени, тайминговые каналы;
- деплой и настоящие вызовы LLM в тестах.

## Decisions

### 1. Владелец проекции заявки (IR-01)

В `saveObject` чтение существующей строки возвращает и `user_id`. Если строка есть и `user_id <> object.UserID`, функция возвращает `actions.ErrContract` до любых записей. Upsert дополнительно получает условие `DO UPDATE … WHERE service_objects.user_id = EXCLUDED.user_id`. Это защита от гонки двух вставок: при нуле затронутых строк — тоже `ErrContract`.

Последствия идут по существующим путям:

- worker: `Finish` вернул ошибку → `Uncertain` → сверка → по исчерпании `manual_review`. Успех не показывается, повтор с новым ключом не создаётся;
- refresh: `ApplyObject` вернул ошибку → задание завершается с `SERVICE_UNAVAILABLE`, план не меняется.

Альтернатива — первичный ключ `(service, object_id, user_id)` с миграцией. Отклонена: она разрешила бы двум пользователям держать одну заявку и не сделала бы конфликт видимым. Ещё одна альтернатива — молча игнорировать чужой объект. Отклонена: для подтверждённого действия это выглядело бы как потерянный ответ без сверки.

### 2. Личный идентификатор сообщения (IR-03)

Внутренний `messages.id` остаётся для связей в БД. Наружу он не сериализуется: `actions.Message.ID` получает тег `json:"-"`, а JSON-поле `id` берёт значение `Sequence` (отдельное поле DTO, заполняемое в `scanMessage`). `message_id` и `message_ids` в ответах `message` и `button` возвращают `m.Sequence`.

Тип остаётся целым, Zod-схемы фронтенда не меняются, React-ключи остаются уникальными внутри ленты. Значения в истории не пересчитываются: `sequence` уже сохранена у каждой строки.

Альтернатива — UUID для сообщений. Отклонена: нужна миграция и смена типа в схемах фронтенда, а выигрыша против личной `sequence` нет. Курсор `after` уже работает по `sequence`, так что API становится согласованнее.

### 3. Выборка по владельцу в OfferNext (IR-02)

- Основной запрос: `JOIN cards c ON c.id::text = d.payload->>'card_id' AND c.user_id = d.user_id`; во всех подзапросах `attempts` — `AND a.user_id = d.user_id`.
- Статус первой карточки переноса: `SELECT state FROM attempts WHERE card_id=$1 AND user_id=$2 …` с `user`. Чужая карточка даёт «нет попытки», статус не `succeeded`, и перенос останавливается штатным сообщением владельцу, без перехода ко второму действию.

Других чтений без владельца в фоновых путях ревью не нашло. Новые запросы пишутся по тому же правилу.

### 4. Профиль вкладки (IR-04)

**Бэкенд.** Необязательный заголовок запроса `X-Buddy-Profile: <user_id>`. Проверка встроена в `authenticate` после разрешения сессии:

- нет заголовка — как прежде;
- заголовок совпадает с `profile.ID` — как прежде;
- не совпадает — `409 PROFILE_CHANGED` с обычным телом ошибки без данных профиля. Обработчик дальше не выполняется, поэтому ни чтения, ни записи не происходит;
- нет сессии — `401`, как прежде.

`guard` добавляет `X-Buddy-Profile` в `Access-Control-Allow-Headers`. `login`, `logout` и `/demo/docs/{id}` заголовок не используют: документы открываются ссылкой в новой вкладке. Код добавляется в карту `errorText` фронтенда.

**Фронтенд.**

- `client.ts` хранит `expectedProfile` (id или `null`). Значение выставляется по успешному ответу `/me` и `/demo/session`, сбрасывается в `resetSession()`. `request()` добавляет заголовок, когда значение задано.
- Ответ с кодом `PROFILE_CHANGED` вызывает зарегистрированный обработчик `onProfileChanged`. Он делает тот же сброс, что `changeProfile` без входа: `resetSession`, `cancelQueries`/`clear`, очистка локального состояния и Zustand, новое `epoch`, повторный `/me` уже без заголовка. Пользователь видит уведомление «Профиль сменён в другой вкладке. Данные обновлены.».
- Вызвавшее действие завершается ошибкой с этим же текстом и не повторяется.

Альтернатива — отдавать владельца в теле ответа и сверять на клиенте. Отклонена: она не защищает изменяющие запросы, так как сообщение уже было бы сохранено от имени нового профиля. Ещё одна альтернатива — `BroadcastChannel`. Это полезное дополнение для мгновенной реакции, но без серверной проверки не даёт гарантии, поэтому вне области.

### 5. ADR 0012

Новый ADR `docs/adr/0012-data-isolation.md` фиксирует:

- правило «каждая выборка — по владельцу, включая фоновые»;
- личные идентификаторы в API;
- заголовок профиля вкладки;
- решение по IR-05: ключи операций имитаций глобальные, доверие держится на `SERVICE_SECRET`, при корпоративном сервисе — ключи в пространстве владельца или подписанный токен пользователя.

## Risks / Trade-offs

- **Смысл поля `id` сообщения меняется** (тип прежний). Риск для внешних клиентов отсутствует: потребитель API только фронтенд, и он использует `id` как ключ. Существующие Go-тесты, которые берут `message_id` из ответа и ищут по нему строки в БД, нужно перевести на `sequence` или на поиск по `client_message_id`.
- **Ложные `PROFILE_CHANGED`** при штатной смене профиля в той же вкладке. Их предотвращает сброс `expectedProfile` в `resetSession()` до входа. Отдельный тест проверяет, что быстрая смена Алина → Максим не показывает уведомление о другой вкладке.
- **Конфликт номера заявки** уводит подтверждённую попытку в сверку и `manual_review`. Это осознанно: исход действительно неясен, и стажёр видит контакт для ручной проверки.
- **Новый заголовок CORS** нужен только при отдельном `VITE_API_BASE_URL`. При общем origin через nginx изменений конфигурации нет.
