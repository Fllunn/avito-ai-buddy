# AI-buddy — ИИ-наставник для стажёров

Прототип для Hack&Change 2026: помогает стажёру найти следующий шаг, разобраться в демонстрационных материалах и выполнить организационное действие через имитации корпоративных сервисов. Снимает рутину с наставника, сохраняя за ним содержательное сопровождение.

Работают веб-чат, панель онбординга, доступ, отгул, отмена и перенос с подтверждениями и сохранёнными результатами. Все данные синтетические. Проверенный режим LLM — **fake**. Адаптер OpenRouter реализован и проверен fake HTTP; реальная модель и её качество пока не проверялись. Change ещё требует человеческой приёмки.

## Запуск с нуля через Docker

### 1. Подготовить окружение

Установить и запустить Docker Desktop на macOS/Windows либо Docker Engine с плагином Compose v2 на Linux. Команды ниже рассчитаны на Bash: в Windows выполнять их в WSL2 с доступом к Docker. Для скрипта настройки нужны `openssl`, `awk` и `mktemp`; `make` используется как сокращение команд и необязателен.

Проверить, что Docker запущен и Compose доступен:

```bash
docker --version
docker compose version
docker info
```

Compose должен поддерживать `up --wait`; для альтернативных конфигураций также нужны YAML-теги `!reset` и `!override`. Если команда или тег не распознаются, обновить Compose v2. **Go, Node.js, npm, PostgreSQL и Redis для этого способа не нужно устанавливать на компьютер**: сборка и сервисы работают в контейнерах. При первом запуске нужен интернет для загрузки образов и зависимостей.

### 2. Получить проект и перейти в его корень

```bash
git clone https://github.com/Fllunn/avito-ai-buddy.git
cd avito-ai-buddy
```

Если проект уже скачан или получен ZIP-архивом, достаточно открыть терминал в распакованной папке. В текущем каталоге должны находиться `README.md`, `Makefile` и `compose.yaml`. Все дальнейшие команды выполнять из него.

### 3. Создать локальную конфигурацию

```bash
make demo-env
```

Если `make` не установлен:

```bash
bash scripts/init-demo-env.sh
```

Скрипт создаёт `.env` на основе [.env.example](.env.example), генерирует отдельные случайные `SERVICE_SECRET` и `DEMO_ADMIN_SECRET`. Существующий `.env` сохраняется без изменений.

Перед первым запуском открыть `.env` в редакторе и заменить три примерных пароля на собственные: `POSTGRES_PASSWORD`, `API_DB_PASSWORD`, `MOCKS_DB_PASSWORD`. Для каждого можно получить отдельное значение командой `openssl rand -hex 24`. Для двух последних использовать буквы, цифры, дефис или подчёркивание: Compose подставляет их в URL подключения. В Docker-конфигурации эти URL собираются автоматически.

Для первого знакомства оставить:

```dotenv
DEMO_MODE=true
DEMO_NOW=2026-11-12T12:00:00+05:00
DEMO_TIMEZONE=Asia/Yekaterinburg
LLM_PROVIDER=fake
```

Режим `fake` работает без ключа и платных вызовов LLM. Демо-дата намеренно зафиксирована, чтобы примеры доступа и отгула воспроизводились; длительности и таймауты измеряются реальным временем. Настройка OpenRouter описана ниже в разделе «Конфигурация и LLM».

`.env` содержит локальные секреты: не публиковать его и не добавлять в git.

### 4. Собрать и запустить все сервисы

```bash
docker compose config --quiet
make up
```

Эквивалент запуска без `make`:

```bash
docker compose up -d --build --wait
```

Команда собирает backend, имитации и frontend, запускает PostgreSQL и Redis, применяет миграции и загружает синтетические данные. Отдельно запускать миграции, устанавливать npm-зависимости или создавать базы не требуется. Дождаться завершения команды; первая сборка может занять несколько минут.

Проверить результат:

```bash
docker compose ps
curl --fail http://localhost:8080/readyz
```

В `ps` должны работать пять сервисов: `postgres`, `redis`, `mocks`, `api`, `frontend`, со статусом `healthy`. API готовности возвращает `{"status":"ready"}`.

### 5. Открыть приложение и попробовать сценарий

| Что открыть | Адрес |
|---|---|
| Рабочее пространство стажёра | [localhost:5173](http://localhost:5173) |
| Панель ведущего: согласования и сбои | [localhost:8081/demo](http://localhost:8081/demo) |
| Проверка готовности API | [localhost:8080/readyz](http://localhost:8080/readyz) |

В приложении выбрать **«Алина · стажёр · Платежи»** в поле «Демо-профиль». Появятся главный следующий шаг, чат и кнопка «Мой онбординг». Нажать «С чего начать?» или «Нужен доступ». Подготовка карточки ещё не отправляет заявку: сначала проверить параметры и отдельно подтвердить действие.

Для входа в панель ведущего использовать значение `DEMO_ADMIN_SECRET` из своего `.env`. Там можно согласовать созданную заявку. Затем в приложении открыть «Мой онбординг» и нажать «Проверить статусы». Полные примеры приведены в следующем разделе «Проверка трёх сценариев».

PostgreSQL и Redis при необходимости доступны с компьютера на `localhost:15432` и `localhost:16379`; для работы через браузер подключаться к ним не нужно. Открывать интерфейс именно через `localhost`, как в ссылках: другой origin должен быть отдельно разрешён конфигурацией API.

### 6. Остановить, продолжить или обновить

```bash
docker compose stop          # остановить, сохранив контейнеры и данные
docker compose up -d --wait  # продолжить с прежними данными
docker compose down          # удалить контейнеры и сеть, сохранить тома с данными
make up                      # пересобрать после изменения кода и запустить
```

История, сессии и заявки хранятся в томах PostgreSQL/Redis и сохраняются после обычного `stop` или `down`. Команда `down --volumes` удаляет эти данные — для обычного завершения работы её использовать не нужно.

**Полный сброс демонстрационных данных** выполнять только осознанно:

```bash
make demo-reset CONFIRM=demo
# Без make: bash scripts/demo-reset.sh demo
```

Сброс останавливает обработчики, очищает данные обеих БД, сессии, историю, заявки, ключи и Redis, затем заново мигрирует, сидирует и проверяет готовность. При частичном сбое обработчики остаются остановленными; устранить причину и повторить всю команду. Сброс данных приложения не пересоздаёт пароли ролей PostgreSQL: изменение паролей в `.env` само по себе не меняет пароли в уже созданном томе.

### Если запуск не получился

Сначала проверить состояние и последние сообщения сервисов:

```bash
docker compose ps -a
docker compose logs --tail=100 api mocks postgres frontend
```

| Симптом | Что проверить |
|---|---|
| `Cannot connect to the Docker daemon` | Запущен ли Docker Desktop/Engine; выполняется ли `docker info`. |
| `make: command not found` | Использовать приведённые выше команды `bash scripts/init-demo-env.sh` и `docker compose up -d --build --wait`. |
| Неизвестный `--wait`, `!reset` или `!override` | Обновить плагин Compose v2; команда должна называться `docker compose`, с пробелом. |
| `Set … in .env` или ошибка конфигурации | Проверить, что `.env` создан в корне проекта и содержит нужные значения из `.env.example`; скрипт не дописывает существующий файл. |
| `port is already allocated` / `address already in use` | Проверить порты 5173, 8080, 8081, 15432 и 16379. Остановить занимающий их свой процесс либо использовать альтернативную конфигурацию ниже. |
| Ошибка пароля PostgreSQL после изменения `.env` | Вернуть значения, с которыми создавался том. Сброс данных приложения не исправляет несовпадение паролей; удаление тома допустимо только при готовности потерять его демо-данные. |
| Страница открылась, но действия получают 403 | Использовать `http://localhost:5173` и проверить `ALLOWED_ORIGIN`; для панели — `DEMO_PANEL_ORIGIN`. |
| Сервис `unhealthy` или завершился | Смотреть его логи; после исправления конфигурации повторить `make up`. |

Для отдельного экземпляра с другими портами есть [acceptance override](infra/acceptance.compose.yaml):

```bash
docker compose -p ai-buddy-alt --env-file .env \
  -f compose.yaml -f infra/acceptance.compose.yaml up -d --build --wait
```

У него собственные тома, UI на [localhost:15173](http://localhost:15173), API на [localhost:18080](http://localhost:18080/readyz), панель на [localhost:18081/demo](http://localhost:18081/demo). Этот override явно включает `fake` и не публикует PostgreSQL/Redis. Для остановки использовать ту же команду с теми же `-p`, `--env-file`, обоими `-f`, заменив `up -d --build --wait` на `stop` или `down`.

## Проверка трёх сценариев

Для воспроизводимых дат оставьте `DEMO_NOW=2026-11-12T12:00:00+05:00`. Это бизнес-дата; очередь и таймауты используют реальные операционные часы.

1. **Ориентирование.** Войти как Алина, нажать «С чего начать?» или спросить о следующем шаге. Проверить собственный план, зависимости и «Ждём от других». Спросить про регламент доступа, открыть источник. Контакты и материалы обозначены как демонстрационные.
2. **Доступ.** В форме выбрать пространство команды Платежей, уровень чтения, обоснование «Для знакомства с документацией команды». Создать карточку, проверить параметры и подтвердить. Появится номер заявки со статусом «Создана», а не «Доступ выдан». В панели ведущего одобрить её. Вернуться и нажать «Проверить статусы»: P6 выполнен, P7 доступен. Постоянный опрос согласований не обещается; обновление выполняется по кнопке/при открытии плана.
3. **Отгул.** Указать 13–16 ноября 2026: два рабочих дня, причина не собирается. Подтвердить карточку: результат submitted. Одобрить в панели и обновить статусы. Перенести на 20 ноября: каждое из двух действий требует отдельного подтверждения. Для непересекающихся дат сначала создаётся новый запрос, затем отменяется старый; при пересечении порядок обратный. Отказ от второго действия сохраняет уже полученный результат. Отменить будущий запрос отдельной карточкой, обновить страницу и проверить историю.

Для свободного диалога доступны реплики «Нужен доступ в пространство команды», «Хочу отгул», «Кто мой наставник?». Недостающие параметры уточняются; при сбое LLM остаются формы. Короткое «да» не подтверждает произвольную старую карточку после смены темы. После отказа сервиса повторная подача требует явного продолжения либо нового обоснования.

Открыть карточку в двух вкладках, изменить в одной и подтвердить старую в другой: ожидается ошибка версии без второй операции. Перезапустить Compose без сброса: история и результаты остаются. Для потери ответа выбрать в панели lose_response_after: бот покажет неизвестный исход и сверит прежний ключ, не создавая дубликат. unavailable_before допускает повтор той же попытки; длительная неопределённость требует ручной проверки. Новая карточка не обходит незавершённую попытку.

## Конфигурация и LLM

Все настройки — в [.env.example](.env.example). Секреты задаются окружением. `SERVICE_SECRET` общий для API/имитаций; `DEMO_ADMIN_SECRET` — отдельный вход ведущего. `ALLOWED_ORIGIN` совпадает с origin страницы. Cookie HttpOnly/SameSite=Lax, Secure для HTTPS; в БД хранится хеш токена.

Для OpenRouter задать на сервере `LLM_PROVIDER=openrouter`, `LLM_MODEL=<идентификатор модели>`, `OPENROUTER_API_KEY`, пересоздать API. Модель должна поддерживать JSON-ответы. Конкретная модель не закреплена. Ошибка конфигурации останавливает запуск; незаметной подмены real на fake нет. Ключ не передаётся frontend и имитациям. [ADR о протоколе, ограничениях и тарифах](docs/adr/0010-openrouter-provider.md). Автотесты не вызывают платную модель.

`LLM_TIMEOUT`, `SERVICE_TIMEOUT`, `CARD_TTL`, `STEP_CONFIRMATION_TTL`, `SESSION_TTL`, `RECONCILE_DELAYS` проверяются при запуске. `DEMO_NOW` и `DEMO_TIMEZONE` должны совпадать у API и имитаций. При отдельном размещении frontend `VITE_API_BASE_URL` задаётся при сборке, API разрешает соответствующий origin. После смены профиля Query/Zustand очищаются, запросы отменяются, поздние ответы отбрасываются; уже подтверждённая работа сохраняет исходного владельца.

## Проверки и отчёты

Следующие команды выполняют Go/Node-инструменты на компьютере. Для них, в отличие от запуска через Docker выше, нужны Go 1.27.0, Node.js 24.22.0, npm 11.19.1 и `make`; сначала установить зависимости фронтенда командой `cd frontend && npm ci`, затем вернуться в корень проекта.

```bash
make coverage         # полные тесты, race, отдельные PostgreSQL/Redis и покрытие
make integration-test # Go-проверки с настоящими изолированными хранилищами
make build            # Go и TypeScript/Vite
make infra-check      # изоляция БД и сохранение томов в отдельном проекте
make metrics          # технические прокси из текущей демонстрационной БД
```

`make test` без тестовых URL пропускает интеграционные Go-проверки; итоговый прогон — make coverage. Реальная LLM в тестах не вызывается. Отчёт `coverage/summary.json` считает исполняемые строки backend/frontend/mocks и взвешенную сумму; каждый порог строго >80%. Go-блоки объединяются по исходнику, строка покрыта только при исполнении всех её блоков. Нативная статистика операторов сохраняется отдельно в coverage/*-native.txt. Исключения: тесты, зависимости, testdata, сгенерированные файлы и проверенные точки входа без прикладной логики; неимпортированные исходники включены. Фикстуры проверяют частичное покрытие строки и границу ровно 80%.

Браузерные сценарии: [acceptance.mjs](frontend/test/e2e/acceptance.mjs), [resilience.mjs](frontend/test/e2e/resilience.mjs). Они работают на выделенном локальном синтетическом стенде; инструкции и фактические результаты — [docs/verification](docs/verification/WORK_STATE.md). [Измерения p95](docs/verification/performance.json), [сквозная проверка](docs/verification/acceptance.json). Эти измерения не доказывают экономию времени наставника. Определения прокси и план пилота — [metrics.md](docs/metrics.md).

## Разработка и добавление материала

Go 1.27.0; Node 24.22.0/npm 11.19.1; PostgreSQL 16.6; Redis 7.4.1; React 19.3.1/TypeScript 5.9.3/Vite 8.3.8. Прямые версии закреплены в go.mod и package.json, транзитивные — в go.sum/package-lock.json. Воспроизводимая установка frontend: npm ci. Локальная разработка: npm run dev в frontend, API на :8080 через Vite proxy.

Демонстрационные материалы задаются в backend/platform/demo и сидируются в PostgreSQL. Новый материал должен иметь ID, команду/область видимости, владельца, дату и признак demo; добавить фрагменты и ключевые слова, тесты поиска и прав для обеих команд. Сид не перезаписывает существующие записи: новую начальную версию проверить через полный сброс выделенного стенда. Ссылка /demo/docs/{id} проверяет права на сервере. Не выдавать материал за реальный регламент Авито.

[Архитектура](docs/architecture.md), [контракты имитаций](mocks/README.md), [правила проекта](AGENTS.md). OpenSpec: [утверждённый change](openspec/changes/build-onboarding-prototype/), текущие спеки попадут в openspec/specs после человеческой приёмки и архивирования. Агент не делает commit/push/PR; эти действия и загрузку комплекта на платформу выполняет человек.

## Комплект для сдачи

`python3 scripts/package-submission.py` создаёт `output/submission/ai-buddy-submission.zip` с исходниками, README, конфигурацией-примером, сидами, OpenSpec, отчётами, PDF и MP4. Скрипт проверяет структуру ZIP и создаёт manifest.json с SHA-256. Локальные .env, зависимости, .git, бинарники и промежуточные записи исключены. Перед сборкой должны существовать финальные отчёты покрытия, PDF и видео.

На платформу загрузить ZIP. Альтернатива — PDF и ссылка на репозиторий с этой же принятой версией. Для приватного репозитория человек предоставляет доступ аккаунту жюри `hack-and-change-2026`. Коммит и push выполняет человек; агент не меняет удалённый репозиторий. Наличие локального ZIP не означает публикацию или приёмку.

## Личное пространство и карта запроса

Change [redesign-buddy-experience](openspec/changes/redesign-buddy-experience/tasks.md) добавляет один главный следующий шаг, сводку текущего периода, отдельный полный план, формы с сохранением ввода, локального маскота «Спутник» и карту сохранённых фактов. Подтверждение остаётся обязательным; версии, дедупликация, права и сверка сохраняются. Маршрут различает ожидание пользователя/сервиса, отказ, ошибку и неизвестный исход. Операция завершается после сохранённого результата, а согласование заявки показывается отдельно.
